# Organessônium

Este repositório contém a versão desktop C# WPF + WebView2 do Organessônium. O aplicativo usa o Discord como armazenamento de payloads, com um índice hierárquico por pasta para que a abertura da raiz não dependa da quantidade total de arquivos no servidor.

## Requisitos

- Windows 10 versão 2004 (build 19041) ou posterior, x64.
- [.NET SDK 10.0.401](https://dotnet.microsoft.com/download), fixado em `global.json`.
- Git.
- WebView2 Runtime para executar a interface.
- Windows 10/11 SDK instalado pelo Visual Studio Installer, necessário apenas para gerar MSI/MSIX.
- Ativos de mídia verificados, necessários apenas para a compilação de distribuição.

## Compilar e executar

```powershell
git clone https://github.com/Matehfields/Organessonium-desktop.git
cd Organessonium-desktop
dotnet restore Organessonium/Organessonium.slnx
dotnet build Organessonium/Organessonium.slnx -c Release
dotnet run --project Organessonium/Organessonium/Organessonium.csproj
```

O código compila em um clone limpo. O runtime do FFmpeg e as fontes correspondentes não são versionados; a geração da distribuição completa exige os ativos descritos em [docs/MEDIA-ASSETS.md](docs/MEDIA-ASSETS.md). A restauração usa apenas o feed oficial do NuGet definido em `NuGet.config`.

## Testes

Suíte rápida, sem FFmpeg, mídia ou janelas:

```powershell
pwsh ./tools/run-tests.ps1 -Configuration Release -SkipMedia
```

Acrescente `-IncludeUi` para os testes que abrem janelas WebView2. Os testes de mídia exigem `runtime-package.zip` e, em alguns casos, `ffprobe.exe` de uma distribuição completa do FFmpeg. Consulte [git.md](git.md) para os detalhes e limitações.

## Versionamento

`Version.props` é a única fonte da versão pública e do número de build. Não edite números de versão em `.csproj`, scripts ou manifests.

```powershell
pwsh ./tools/version.ps1 show
pwsh ./tools/version.ps1 bump-build -ExpectedBuild <build-lida-no-inicio>
```

- A versão pública segue SemVer e só muda com autorização explícita do mantenedor.
- A build é incrementada exatamente uma vez por rodada concluída, antes do commit correspondente.
- Derivados: `AssemblyVersion A.B.C.0`, `FileVersion A.B.C.build`, `InformationalVersion A.B.C+build.N` e pacotes Windows `A.B.C.0`.

## Arquitetura de dados

`DiscordApiClient` adiciona a autorização do bot somente às requisições destinadas à API
HTTPS do Discord. As leituras de anexos usam um cliente separado, sem o token do bot.
Ele valida HTTPS e o domínio do CDN em cada requisição e redirecionamento.

- `Bridge/AppController.cs` coordena upload, download, previews, transferências e a ponte WebView2.
- `DesktopEntryPoint.cs` inicia o coletor temporário `Services/Diagnostics` antes de criar `App`; o coletor observa falhas, tempos e responsividade sem controlar os fluxos de negócio.
- `Services/ForumUploader.cs`, `ForumUploader.MultiAttachment.cs` e `ForumUploader.Shared.cs` preservam o transporte dedicado e encaminham arquivos elegíveis à fila compartilhada, com até dez attachments criptografados independentes por mensagem.
- `SharedStorageManager` e seus módulos `Recovery`, `Cleanup`, `Mutations`, `Reads` e `ReferenceScan` mantêm catálogo remoto, reservas, referências e limpeza recuperável; `SharedPayloadBatcher` agrega descriptors por pool sem juntar plaintexts.
- `Services/UploadPartContent.cs` prepara e transmite anexos sob demanda; `UploadBodySlot.cs` separa workers de transmissão das respostas ainda pendentes.
- `Services/ForumDownloader.cs` resolve mensagens e attachments referenciados pelo metadata; `ForumDownloader.Discovery.cs` busca as referências em janelas limitadas enquanto a fila contínua baixa as partes. `ForumDownloader.Direct.cs` autentica as partes em RAM e coordena gravação, retomada e finalização sem montagem. `DownloadFileLayout` publica intervalos imutáveis de 64 bits; `PartialDownloadFile` mantém um handle e escreve regiões independentes com `RandomAccess.WriteAsync`.
- `Services/AppRegistry.cs` resolve o mapa `folderId -> threadId`, abre somente o índice da pasta requisitada no fórum `folders` e atualiza os caches afetados por cada operação.
- `Services/MetadataService.cs` publica e lê o mapping no `names` e os metadados de filhos diretos nos threads de índice de `folders`.
- `Services/SerialIndexService.cs` lê, valida, mantém em memória e publica o serial binário de uma única pasta por vez no canal `serial`.
- `Services/FolderSerialCodec.cs` codifica e decodifica o formato binário versionado `OSER` usado pelos seriais.
- `Services/SettingsStore.cs` mantém configurações, os caches locais `app_entries` e `folder_index_map`, previews e estados de transferência no diretório de dados.
- `Services/VideoStreamSession.cs`, `VideoChunkIndex.cs` e `DiscordVideoChunkProvider.cs` expõem o vídeo como arquivo virtual assíncrono, com chunks autenticados em RAM.
- `Services/PreviewResourceRegistry.cs` e `Bridge/WebView2PreviewAdapter.cs` entregam prévias por host HTTPS virtual interceptado pelo WebView2, sem servidor local.
- `Services/Mp4FastStart.cs` prepara MP4 elegível por leitura virtual antes do upload, preservando os payloads de áudio/vídeo.
- `Services/FfmpegMediaService.cs` executa o motor de mídia separado/oculto, extrai miniaturas e entrega MP4 fragmentado por pipe; `FfmpegPreviewUpload.cs` gera a prévia completa em staging oculto ao lado da origem e a envia com buffers limitados. `VideoPreviewGenerator.cs` gera imagens comuns dentro do processo com decodificação reduzida. `VideoPreviewWorker.cs` conserva o fallback Windows isolado, sem janela ou saída temporária.
- `Services/VideoPlaybackProgress.cs` salva e restaura a posição local de reprodução por `fileId`.
- `Services/Sync/SyncBackgroundHost.cs` mantém o sincronizador sem depender da janela; `SyncEngine`, `SyncPlanner`, `SyncScanner` e `FolderWatcher` detectam, comparam e aplicam alterações.
- `Services/Sync/SyncStateStore.cs` persiste vínculos, estado-base e decisões; `CloudSyncRepository.cs` reutiliza chunks, criptografia, transferências e índices do Discord.
- `Services/AppRegistry.Sync.cs` integra computadores e árvores sincronizadas à aba Dispositivos; `Bridge/AppController.Sync.cs` e `web/sync.js` apresentam os comandos, estados e conflitos.
- `App.Background.cs`, `MainWindow.Sync.cs`, `TrayManager`, `SingleInstanceHost` e `StartupManager` separam o ciclo de vida gráfico da execução em segundo plano.

Um arquivo é identificado por `fileId`; seu metadata associa esse identificador ao `threadId` de payload, às referências dos chunks, ao nome e MIME originais, ao tamanho original `sizeBytes`, ao `parentFolderId` e às referências de prévias. Uploads novos usam `chunkRefs: [{ index, messageId, attachmentId }]`, com índice zero-based e identificação exata do anexo; arquivos antigos continuam usando `chunks: string[]`, um attachment por mensagem. Pastas usam `folderId`; o `parentFolderId` estabelece a árvore. Os IDs são preservados em rename e move. Novas publicações de metadados são cifradas integralmente com encrypted metadata V1; o desktop autentica e descriptografa antes de localizar os blobs. JSON antigo em claro continua sendo lido, sem migração ao abrir.

### Armazenamento compartilhado V2

Novos conteúdos de até 1 GiB original, inclusive o limite exato, usam pools no fórum `files`; conteúdos maiores continuam dedicados. Cada pool guarda até 256 fileIds distintos, incluindo reservas/históricos ainda retidos. Chunks, versões e previews não ocupam vagas adicionais. `storage: { version: 2, mode: "shared", storageId }` identifica o layout no metadata e nos snapshots; dedicado novo usa `mode: "dedicated"`. Ausência de storage continua sendo legado dedicado, sem migração automática. O documento completo de interoperabilidade é [Armazenamento compartilhado V2](#armazenamento-compartilhado-v2).

O controle inicial shared é cifrado e não tem attachment. O catálogo cifrado `storageThread` e o journal operacional V2 ficam em uma thread técnica de índice no fórum `folders`, identificada pelo mapping `folderId: storage-v2`. Somente esse mapping é publicado em `names`; não existe card dessa pasta na biblioteca. Metadados de cada arquivo continuam no índice da respectiva pasta. O catálogo guarda ownerId, thread/control IDs, revision, estado e membros/pendingVersions. SQLite não decide a capacidade: o documento remoto selecionado é relido antes de alterá-la. O owner é UUID persistido por instalação, vinculado ao MachineGuid/SID no desktop. Só esse escritor reserva/transmite/limpa fisicamente o pool. Outra instalação cria pools com identidade diferente; reads, organização e versões continuam compatíveis. Não há CAS/transação distribuída no Discord, nem adoção automática de identidade perdida.

`storageBatchPlan` cifrado registra fileId/versionId/role/index/count/filename/tamanho antes de cada multipart. `storageBatchReceipt` vem depois de validar toda a resposta e antes dos checkpoints participantes. Isso permite reparar ACK/checkpoint perdido sem reenviar chunks confirmados. Uma fila limitada agrega partes de arquivos/roles distintos. Dez anexos disparam o envio; os 250 ms reavaliam o lote parcial, sem fechá-lo enquanto houver produtores previstos naquele pool. Um arquivo de parte única, ou a sobra final de partes únicas cujos produtores são conhecidos, é despachado assim que não há outros arquivos previstos, sem aguardar essa janela. Antes disso, a fila é drenada novamente para incorporar descritores que acabaram de ser admitidos. A espera reutiliza a notificação do canal e um temporizador, sem cancelar uma operação a cada intervalo. Preparação ou admissão de original bloqueadas permitem drenar a sobra após cinco segundos, evitando espera circular por recursos. Esse prazo não fragmenta o lote se restarem somente produtores ainda não admitidos e houver publicação de metadados em andamento, independente dos anexos pendentes. Cancelar ou esgotar os produtores também permite o lote final. Grandes dedicados mantêm seu transporte anterior.

Thumbnails shared usam `preview.thumbnailRef: { messageId, attachmentId }`, nunca seleção pelo primeiro anexo. 480p conserva `preview.video480p.chunkRefs`. DTOs são resolvidos por `(threadId,messageId)` com cache limitado/deduplicado; cada download usa attachmentId e contexto criptográfico do arquivo/versão. CDN expirada renova o mesmo ID. A UI usa requestId do metadata/arquivo, e o cache da miniatura inclui fileId, versionId e os dois IDs do anexo, evitando colisões entre cards do mesmo pool. OSER continua v3; seus consumidores hidratam detalhes quando necessário.

Exclusão definitiva persiste `storageCleanup` antes de retirar metadata, depois registra released. GC verifica índices remotos, versões, trash, revisões sync, claims, reservas e referências de upload/download/preview. Em shared, faz PATCH somente com IDs dos attachments a conservar, relê/confere o snapshot e valida a resposta. Só uma mensagem vazia é removida, nunca o controle/post. Erro mantém intent para retomada; 404 confirmado do locator permite recuperar a janela entre exclusão de metadata e released. Pools de outro owner, reads/claims externos e POSTs inconclusivos permanecem pendentes. O item sai do índice antes da liberação física; pendências e novas tentativas permanecem silenciosas, sem arriscar attachments de outros arquivos.

Claims de metadata, fences de exclusão, planos, recibos e referências de leitura são eventos cifrados no índice técnico `storage-v2`, não em `names`. Alteração concorrente retorna conflito; publicação de versão revalida conteúdo sob claim. Leases de escrita por conta/thread impedem arquivamento durante atividade e só desarquivam quando necessário, respeitando locked/403. Reads não reativam o pool: registram referência no índice técnico, liberada ao concluir/fechar, ou conservada com checkpoint pausado. Reinício reconcilia operações desse owner; não expira referências estrangeiras por relógio. O leitor também aceita registros V2 antigos em `names`, sem criar ou atualizar esses registros nesse canal; um catálogo antigo efetivamente modificado passa a ser publicado no índice técnico. Não há exclusão automática dos registros antigos. O número de mensagens do journal inclui confirmações e eventos intermediários e pode ultrapassar o número de arquivos da biblioteca. A enumeração de todos os índices/pools para prova de GC ocorre somente quando há limpeza pendente, não para renderizar a raiz.

A manutenção explícita `tools/NamesScanner --migrate-storage-journal` transfere o journal V2 antigo de names para o índice técnico, com o app fechado. Copia e autentica todos os destinos antes de iniciar remoções; confere origem/destino novamente por registro e preserva mappings e blobs. O marcador cifrado `legacyNamesMessageId` permite retomada idempotente e preserva a ordem lógica dos eventos. Os modos `--audit-metadata-layout` e `--audit-storage-journal` são somente leitura e imprimem contagens por tipo, respectivamente de names e de names mais o índice técnico. O comando não transfere metadados `file`/`folder` legados para o índice técnico; tais objetos exigem migração por pasta. O protocolo e o procedimento estão em [Armazenamento compartilhado V2](#armazenamento-compartilhado-v2).

## Índice serial

Cada pasta, inclusive `root`, possui exatamente um serial `.bin`. O localizador `folderSerial` mostra `name` e `folderName`, junto de `folderId` e SHA-256 do anexo cifrado; o anexo `serial.bin` contém o envelope JSON V1 em UTF-8, que revela `folderSerialData` com OSER em Base64 após autenticação. Internamente, OSER guarda os filhos diretos, IDs, relações, MIME, datas, previews, cores, favorito e agregados. Localizadores cifrados ou em claro e anexos OSER antigos permanecem legíveis. O nome de um serial existente fica visível na próxima publicação desse serial.

O serial é o fast-path persistente. Ele é mantido em `OrganessoniumData\Serials` e, depois da primeira leitura, também em memória durante a sessão. O codec lê `OSER` v1 a v4, mas publica v3 para manter o formato binário compartilhado. `sizeBytes` por filho existe somente em v4; o agregado da pasta preserva o total de bytes. Abrir a raiz lê somente o serial da raiz. Abrir `/Fotos` lê somente o serial de `Fotos`; não lê os seriais das subpastas. Antes de reutilizar o cache, o leitor compara seu SHA-256 com o mapping, uma vez por digest conhecido. Mudança de `serialMessageId` ou digest ao atualizar mappings invalida disco e memória; o leitor baixa somente o anexo indicado pela pasta. A escrita atômica usa um temporário com nome exclusivo e remove-o ao terminar. Antes de reutilizar um serial local durante uma sincronização, o app confirma uma vez por sessão que a mensagem remota indicada pelo mapping ainda existe. Mapping sem `serialMessageId` ou mensagem removida faz o serial ser republicado e o mapping ser atualizado. Os posts do fórum `folders` são arquivados após a leitura e também são reconciliados na inicialização, mantendo os índices antigos fora do limite de posts ativos.

Um serial novo só passa a ser o atual depois que o mapping correspondente em `names` é confirmado. Se essa confirmação falhar, o anexo provisório é removido e o cache local é invalidado para que a próxima reconciliação não trate conteúdo não confirmado como publicado. Após atualizar os mappings na inicialização, uma manutenção em segundo plano remove anexos `folderSerial` duplicados do bot somente quando o mapping atual daquela pasta ainda aponta para o serial preservado. O serial não contém a lista de chunks. A hidratação reutiliza detalhes completos já lidos quando `fileId`, mensagem de metadata, thread, salt e referência de miniatura correspondem ao card atual. Quando necessário, procura o metadata completo primeiro no índice do pai e somente depois em `names` para compatibilidade; um 404 nessa procura não é tratado como corrupção. Uma leitura forçada não usa esse atalho.

A quantidade de arquivos locais não equivale apenas às pastas visíveis da raiz: inclui pastas descendentes, árvores de dispositivos e seriais técnicos/especiais como Favoritos e Dispositivos. O cache não é apagado por exceder uma contagem arbitrária. Os agregados diretos de cada pasta incluem os arquivos atuais, as versões retidas e as prévias de vídeo em 480p de cada conteúdo. Cada arquivo continua contando uma vez. O total do servidor inclui a Lixeira e suas subpastas, com os mesmos arquivos e bytes retidos até a exclusão definitiva; a árvore é visitada uma vez para evitar contagem duplicada. Na leitura remota dos totais, uma pasta sem serial é reconciliada pelo seu índice antes da soma, sem reler os índices das pastas com serial válido. A leitura inicial dos totais em cache continua exclusivamente local.

Quando a mensagem do serial já existe, atualizar seus filhos substitui o anexo `.bin` nessa mesma mensagem e atualiza seu SHA-256 no mapping, preservando o `serialMessageId`. Uma mensagem nova só é criada se não houver referência ou se a mensagem tiver sido removida. A comparação usa os campos efetivamente publicados na versão OSER, incluindo os agregados; valores de tamanho individuais omitidos em v3 não provocam reenvios sem mudança. O cache em memória conserva o mesmo conteúdo codificado do cache em disco.

O botão Atualizar e F5 consultam os mappings e validam os seriais pelo SHA-256 publicado, incluindo Favoritos, Dispositivos e Lixeira. Essa ação alimenta o cache e os cards sem ler as mensagens individuais dos arquivos nem iniciar uma manutenção adicional. Uma pasta sem serial válido conserva o último cache conhecido. Ctrl+F5 é a reconstrução explícita: lê os metadados e gera seriais novos. A navegação comum conserva o fallback de leitura dos metadados quando necessário. Em toda abertura do aplicativo, mesmo quando a leitura inicial de totais falha, uma manutenção silenciosa reconcilia as mensagens dos índices, inclusive Lixeira e Dispositivos, para encontrar inclusões ou remoções que ainda não chegaram aos seriais. Essa conferência é repetida a cada cinco minutos durante a sessão, sem manter o indicador de leitura nem exibir tempo de progresso. Uploads, prévias, downloads e alterações interativas interrompem a manutenção, que aguarda a liberação das operações antes de continuar. Troca de conta e encerramento cancelam o trabalho da sessão anterior. A varredura silenciosa atualiza `app_entries` e a interface quando houver mudança. A publicação dos seriais ocorre nas operações que alteram a biblioteca e na reconstrução explícita. A apresentação inicial da raiz depende de seu serial; a varredura das mensagens ocorre na manutenção silenciosa. Os cards de pastas não exibem contagem de arquivos nem solicitam estatísticas por pasta durante a renderização. Pastas são únicas por pai e nome: uma nova solicitação para a mesma pasta reutiliza o `folderId` existente. Na reconciliação com escrita habilitada, duplicatas legadas podem ser consolidadas na pasta canônica, com os filhos preservados antes da exclusão do metadata, mapping, serial e thread de índice duplicados. Durante essa leitura, a interface mostra carregamento em vez de uma pasta vazia temporária. Uma leitura com mensagens, mas sem nenhum metadata válido, preserva o cache; uma leitura concluída sem mensagens ou com apenas o cabeçalho válido confirma uma pasta vazia e remove os filhos antigos. A tela Arquivos exige associação de `parentFolderId` com a raiz antes de exibir itens nela.

`AppRegistry` deduplica uma reconciliação em andamento por `folderId`. A paginação e o parsing de um thread ou do canal `names` usam `SearchWorkers` com concorrência limitada. `DiscordApiClient` mantém o controle de rota e respeita o `retry_after` de HTTP 429, portanto uma verificação em segundo plano não dispara requisições ilimitadas nem duplica o trabalho de uma navegação.

### Manutenção silenciosa

O janitor da sessão confere os posts dos fóruns de índices e payloads depois da reconciliação silenciosa. Posts inativos são arquivados sob o mesmo controle de leases de escrita; threads bloqueadas e índices de upload abertos são preservados. O arquivamento também abrange pools inativos de outros owners e conserva sua identidade e conteúdo. O controle inicial de um pool contém storageId, ownerId e versão do layout; identifica o armazenamento e permite recuperação, portanto permanece nos pools válidos. Um pool deste owner sem referências remotas, leitores, alterações pendentes ou escritor ativo pode ser excluído se contiver somente esse controle autenticado, sem anexos ou outras mensagens. O catálogo é fechado antes da exclusão e o transporte revalida o post sob o gate de escritores. Checkpoints locais sem partes confirmadas voltam à reserva pendente, mantendo arquivo, versão, chave e origem; uma retomada também trata um destino vazio já removido antes de o checkpoint ser atualizado. Pools estrangeiros e candidatos com conteúdo incerto permanecem preservados. A auditoria confronta os índices remotos, incluindo versões, sincronização e Lixeira, com o catálogo e checkpoints, e registra somente contagens técnicas. Ausência em cache ou serial antigo não autoriza exclusão de payloads; a remoção física de anexos continua exigindo intents duráveis e prova de referências. Nenhum painel de progresso é aberto pelo janitor.

A auditoria periódica dos índices percorre até quatro pastas por rodada. Confere cabeçalho, destino, identidades duplicadas e divergências entre o serial autenticado e os metadados remotos. A verificação de anexos roda por amostragem com limite de requisições. O painel de diagnósticos registra as contagens e operações pendentes sem expor dados dos arquivos. Para um inventário manual somente leitura, use `dotnet run --project tools/NamesScanner -- --audit-folder-indexes`. `--journal-only` consulta só o journal e o canal de mappings; `--verify-payloads` inclui a verificação de todos os anexos originais dos índices mapeados.

### Limites e agendamento da API

`Services/DiscordLimits.cs` centraliza os limites de texto (2.000 caracteres), título de thread (100 caracteres), paginação (100 mensagens), anexo (20 MiB por arquivo) e quantidade de anexos (10 por mensagem). Cada chunk desconta os 70 bytes do envelope criptográfico do limite individual; não há bloqueio local de 25 MiB para a soma do multipart. Uploads agrupados procuram completar dez anexos por mensagem, até 200 MiB de conteúdo cifrado; lote final, preparação bloqueada por recursos ou rejeição específica do servidor podem exigir menos anexos. `UploadMessageTargetBytes` acompanha esse total, e `MaxPendingUploadMessages` limita a 64 os lotes em preparação/envio/confirmação, compartilhados entre uploads. Esses 64 lotes são descritores, não 64 buffers de 200 MiB. Metadados maiores que o limite de texto continuam sendo enviados como anexo. Para testar outros valores, altere esse arquivo e recompile. Alterar o orçamento de anexo também altera a divisão dos uploads; transferências já parcialmente confirmadas preservam a divisão registrada no checkpoint.

O limite global documentado pelo Discord é 50 requisições por segundo, não por minuto. `DiscordRequestLimiter` espaça o início das chamadas REST com alvo de 45/s, compartilhado entre clientes do mesmo bot no processo. As cotas por rota são aprendidas pelos headers `X-RateLimit-Bucket`, `Limit`, `Remaining` e `Reset-After`; IDs de mensagens compartilham a rota e canais diferentes mantêm cotas separadas. A cota informada pelo servidor fica separada das reservas em andamento: cada chamada paralela ocupa uma vaga durante o envio, sem descontá-la permanentemente de cada resposta. Headers mais recentes podem recuperar vagas; respostas atrasadas da mesma janela não aumentam a cota. O agendador usa a ordem das requisições, `Date` e os dados de reset quando disponíveis, com tratamento conservador quando faltam timestamps. Enquanto existem chamadas em andamento, a fila reavalia vagas em até 50 ms, sem manter um lock durante a rede. Um HTTP 429 bloqueia novas chamadas desde a leitura dos headers até interpretar `retry_after`, mesmo que outra resposta informe vagas positivas. HTTP 429 global pausa todas as rotas; HTTP 429 local pausa somente o bucket afetado, respeitando o maior `Retry-After`/`retry_after` e uma margem de segurança. Esperas são assíncronas, canceláveis e preservam os callbacks de progresso das transferências. Downloads de anexos pela CDN não consomem essa fila REST. Outros dispositivos usando o mesmo bot não compartilham a fila local, e limites desconhecidos ou alterações do servidor ainda podem produzir 429; nesse caso o app aguarda e tenta novamente.

Para compatibilidade com os seriais existentes, o canal `serial` também aceita os índices globais diretos `favorites` e `synchronized`, sem depender de um mapping desktop. O serial `favorites`, de tipo próprio, mantém a lista plana de itens favoritos. O serial `synchronized` representa a raiz lógica `/@synchronized`; essa raiz técnica não é exibida na tela Arquivos, enquanto seus filhos diretos aparecem em Dispositivos e usam `deviceType` igual a `phone` ou `pc`. Ao abrir Dispositivos, o desktop recompõe os seriais apenas quando encontra filhos diretos de `synchronized` nos metadados de `names`; caso contrário, lê o serial existente e, se ele estiver ausente, os metadados do thread de índice apontado pelo mapping. A presença isolada do metadata da raiz não publica um serial vazio. Os filhos são associados por `folderId` e `parentFolderId`. No formato OSER v3, os bits de favorito, telefone e computador são preservados.

Ao atualizar um serial global existente, o desktop substitui o anexo `.bin` da mesma mensagem do Discord. Para `favorites`, se houver um mapping correspondente em `names`, ele também atualiza o SHA-256 e corrige um ponteiro que tenha ficado apontando para uma mensagem removida.

Os seriais de `favorites` e `synchronized` usam o mesmo cache local persistente dos seriais de pastas. Ao abrir essas abas, o desktop mostra primeiro o serial local válido; uma atualização explícita consulta novamente o servidor. Arquivos, Favoritos e Dispositivos mantêm coleções de interface separadas, de modo que cards de uma aba não entram na contagem ou listagem de outra. A Lixeira apresenta primeiro o cache local, inclusive quando vazio, antes de garantir ou ler seu índice remoto. Depois da primeira apresentação, voltar à aba reutiliza a coleção sem reiniciar a leitura nem o indicador de carregamento. Atualizar e a reconciliação silenciosa continuam atualizando seu conteúdo; uma reconciliação da Lixeira aberta também atualiza seus cards. Leituras concorrentes das abas especiais só publicam a resposta mais recente. A reconstrução de Favoritos consulta somente os índices de origem, nunca o serial global de Favoritos como fonte, evitando reinserir itens removidos.

## Metadados e transporte criptografado

No layout desktop atual, o canal de texto `names` é pequeno e contém mappings `folderId -> threadId`; a mensagem do mapping é um envelope cifrado cujo JSON interno inclui também a referência do serial atual quando ele existir. O ID da própria mensagem de `names` é mantido no cache local para atualização e remoção direta. Para interoperar com metadados publicados diretamente em `names`, o leitor também aceita metadata de arquivo ou pasta nesse canal quando ele é referenciado por um serial global ou de dispositivo. Ao alterar apenas o favorito de um item desse tipo, o JSON remoto original é carregado e atualizado integralmente para preservar chunks, criptografia, previews e todos os demais campos.

O fórum configurado em `foldersForumId` corresponde ao canal `folders` e contém os índices de pasta e a thread técnica `storage-v2`. Cada índice de pasta recebe o título `Nome [folderId]` e uma mensagem inicial `folderIndexHeader`. A publicação de metadados de filhos diretos valida se o `parentFolderId` corresponde ao mapping de destino e ao ID do cabeçalho. Renomear a pasta também renomeia a thread; a auditoria atualiza títulos anteriores quando confirma sua identidade. O índice da raiz de uma pasta sincronizada também recebe revisões `syncRevision` e confirmações `syncApplied`, cifradas nas novas publicações; o marcador textual antigo `syncApplied:<revisionId>` continua legível. Esses registros não viram cards nem entram nos seriais. O fórum configurado em `appsForumId` corresponde ao canal `files` e contém somente os posts de payload usados por upload. O `threadId` de payload indica um post dedicado ou um pool compartilhado por vários arquivos, conforme `storage`; a identidade lógica continua sendo `fileId`. O `threadId` de índice de uma pasta é resolvido pelo mapping em `names`.

Regra principal: a presenca de um campo significa que o recurso existe. A ausencia significa que o recurso nao existe ou nao se aplica.

O metadata novo nao deve incluir campos nulos, arrays vazios, objetos vazios, `enabled = false`, campos temporarios da UI, campos de video em imagens, nem campos de arquivo em pastas. Arquivos e pastas são publicados no thread de índice do respectivo pai, não no `names`. Os exemplos abaixo representam o JSON interno, que é cifrado antes de publicar; não são o conteúdo visível das mensagens novas.

`Services/MetadataEncryption` centraliza o router, envelope, AES-256-GCM, HKDF-SHA256 e erros. O envelope `organessonium-metadata`, versão 1, expõe somente parâmetros técnicos e ciphertext/tag. Usa salt de 16 bytes, nonce aleatório de 12 bytes, tag de 16 bytes, Base64 padrão com padding, UTF-8 sem BOM e AAD definido pela versão. A chave é derivada da master key existente com domínio separado do conteúdo dos arquivos. O modo padrão reutiliza material embutido no app e não é um segredo exclusivo do usuário; confidencialidade baseada em segredo exige chave personalizada. Nenhuma chave vai no envelope.

Arquivos, metadados de pastas, mappings, cabeçalhos, anexos de seriais, revisões e confirmações são protegidos. Títulos dos índices e localizadores de seriais mostram nome e ID da pasta. Posts de payload continuam usando títulos opacos. O backend ainda observa canais/posts, IDs externos, tamanhos, horários e agrupamentos. O cache SQLite e os estados de transferência continuam operacionais e podem conter metadados em claro. Prévias e miniaturas persistidas usam cifra local autenticada; seriais novos locais usam os mesmos bytes cifrados da nuvem. Falhas de versão, chave, tag, Base64 ou JSON não viram pasta vazia nem fazem downgrade para plaintext.

`MetadataService` aplica o codec antes de criar inline ou `metadata.json`, e antes de materializar os objetos. Updates usam PATCH da mesma mensagem, inclusive anexo↔inline; removem attachments anteriores na confirmação, sem apagar o metadata antigo antes do envio. Temporários de metadata contêm somente o envelope cifrado. Leituras não causam migração; uma modificação efetiva publica V1. A especificação criptográfica e o vetor público de teste estão em [Payloads criptografados](#payloads-criptografados). O transporte multi-attachment está em [Upload e transferências](#upload-e-transferências); o inventário de compatibilidades está em [Download, integridade e compatibilidade](#download-integridade-e-compatibilidade).

## Payloads criptografados

Todo novo attachment de conteúdo do Organessônium passa por `EncryptionService` antes de chegar ao Discord: arquivo original, chunks, miniaturas, prévias de imagem, `video480p` e imagens anexadas em Markdown. O JSON interno do metadata recebe o objeto mínimo `encryption` abaixo; o objeto completo é protegido pelo codec de metadados, sem cifrar novamente os chunks:

```json
"encryption": {
  "version": 1,
  "mode": "standard",
  "salt": "base64url-sem-padding-do-salt-por-arquivo"
}
```

O `salt` usa exclusivamente Base64URL sem padding, com os caracteres `A-Z`, `a-z`, `0-9`, `-` e `_`. Esse é o formato gravado nas mensagens do servidor e usado tanto na validação do índice quanto na derivação da chave.

O blob `ORGAESGC` v1 contém magic, versão, papel do payload, índice 1-based e quantidade total do chunk, tamanho plaintext, salt de 16 bytes, nonce GCM de 96 bits, ciphertext e tag de autenticação. O nonce é gerado por CSPRNG para cada payload. A chave por arquivo é derivada por HKDF-SHA-256 a partir da master key, do `fileId` normalizado e do salt do arquivo. O header completo é o AAD do AES-256-GCM, então trocar, truncar ou reordenar payloads invalida a autenticação.

Os attachments criptografados usam nomes técnicos, como `payload.bin`, `chunk-1.bin`, `preview.bin`, `video-preview-1.bin` e `image.bin`, sempre com `application/octet-stream`. O rótulo interno unitário usa `file:<fileId> role:<role> chunk:<parte>/<total> encryption:v1`; um batch usa `chunks:<partes-separadas-por-vírgula>/<total>`. Os números desses rótulos são one-based, enquanto `chunkRefs.index` é zero-based. Ambos ficam dentro de `payloadReference` cifrado nas novas mensagens. O download decodifica esse transporte antes dos parsers existentes; rótulos antigos continuam sendo lidos. Nome, MIME e IDs internos ficam no metadata cifrado.

### Modos de chave

- **Padrão:** funciona automaticamente em instalações compatíveis. A master key é derivada internamente, nunca é exibida, enviada ao Discord ou colocada no metadata.
- **Chave personalizada:** a frase do usuário passa por PBKDF2-HMAC-SHA256 com salt aleatório e 600.000 iterações para produzir uma master key de 256 bits. O SQLite guarda apenas o material protegido pelo DPAPI do Windows para o usuário atual, nunca a frase ou a chave em plaintext.
- **Recuperação:** Configurações permite exportar e importar um arquivo `.organessonium-key` versionado. A configuração inicial reserva uma etapa de segurança, depois do token, para escolher a proteção e importar a chave antes de conectar. Uma biblioteca personalizada exige a chave disponível antes da conexão. Criar uma chave nova requer confirmação de recuperação e não substitui a importação da chave que protege arquivos existentes; repetir a senha gera outro salt e não recupera a master key anterior. Esse arquivo é sensível e deve ser guardado fora do computador, pois permite recuperar arquivos protegidos pela chave personalizada.

O Desktop só exporta `OEK2`. A importação aceita ainda `OEK1` e `ORGKEY` e avisa que esses formatos legados contêm a chave em claro. O Android auditado ainda precisa adotar `OEK2`. As mudanças necessárias estão no [relatório de compatibilidade](docs/COMPATIBILIDADE-MOBILE-DESKTOP.md).

O Desktop arquiva a chave ativa protegida pelo DPAPI antes de ativar uma chave importada. Novos payloads personalizados usam o `keyId` interoperável do Android. A leitura de payloads sem identificador e de metadados V1 pode consultar as chaves históricas locais, validando a autenticação criptográfica. A exportação guarda a chave ativa. Mantenha uma cópia de recuperação de cada chave em uso. Até 32 chaves anteriores podem ser preservadas. Se o limite impedir uma troca, a chave ativa é mantida.

Mudar o modo afeta somente uploads novos. Cada arquivo usa o modo registrado no próprio metadata, sem recriptografar conteúdo existente.

## Upload e transferências

O alvo normal de admissão de memória é 800 MiB para o backend C# e os auxiliares de mídia registrados. O limite Windows de 1 GB é individual por processo desse backend; o WebView2 é observado separadamente e não participa desse teto nem da admissão de buffers. A medição de admissão consulta a memória comprometida do Job Object do backend, com soma dos processos registrados como fallback. Se esse alvo não puder ser recuperado por coleta do heap gerenciado, uma espera de dois segundos permite drenar trabalho usando a margem disponível abaixo do teto, preservando as reservas e 64 MiB de segurança para alocações nativas e do navegador. Os participantes compartilham uma coleta a cada cinco segundos, em vez de dispararem coletas em cada espera. Se não houver reservas ativas para drenar e a margem continuar insuficiente durante 30 segundos, a transferência fica pausada com checkpoint e uma mensagem de memória na interface, em vez de aguardar indefinidamente.

Os ícones das transferências exibem Pausar ao receber o mouse ou foco e Retomar quando pausados. Cada arquivo de um lote pode ser pausado sem cancelar os demais; os checkpoints e anexos confirmados são mantidos, e as vagas de processamento são liberadas durante a pausa. A retomada reutiliza essas partes. Pausar e retomar na mesma sessão conserva a identidade nova do lote e não transforma a publicação em uma recuperação histórica; resultados HTTP inconclusivos continuam exigindo reconciliação remota. Downloads mantêm o arquivo parcial autenticado e retomam as partes pendentes. A confirmação final de metadata de um upload é concluída antes de aceitar outra pausa, evitando interromper uma publicação já iniciada. Cancelar continua sendo uma ação separada, com as preferências de histórico e limpeza existentes.

O planejamento local dos lotes prepara checkpoints com concorrência limitada a oito arquivos e mantém a ordem selecionada. A reserva remota avança por um pool, com até 256 fileIds por post: o próximo pool só é reservado depois de concluir os trabalhos do anterior. A thread técnica do journal permanece sob lease desde a primeira reserva até encerrar o lote, evitando archive/unarchive por registro. Até dez anexos são agrupados por mensagem. Confirmações independentes do journal podem aguardar respostas HTTP em paralelo, sob o limitador global e os buckets do Discord. Identidades novas reservadas pelo lote publicam metadata sem claim de edição; substituições e retomadas conservam claims, fences e confirmações. O cache insere somente a entrada publicada, sem regravar todos os irmãos a cada arquivo. Os cards aparecem por conclusão, e os seriais são publicados ao finalizar a operação.

Upload, retomada e renomeação mantêm um escopo de atualização dos seriais. Os metadados e cards são atualizados por item. Cada serial afetado e Favoritos, quando necessário, são publicados ao encerrar a operação. Leituras concorrentes no mesmo registry também adiam publicações intermediárias. Operações sobrepostas compartilham o escopo e descarregam os seriais após a última conclusão. Cancelamento ou falha publicam o estado das alterações já confirmadas, sem descartar checkpoints nem reverter arquivos concluídos. A limpeza física recuperável continua separada dessa conclusão lógica.

Uploads e alterações interativas de metadados, incluindo criação de pastas, movimentação para a Lixeira e exclusão, têm prioridade sobre a manutenção de limpeza recuperável iniciada em segundo plano. `SharedStorageManager.UploadPriority` coordena essa prioridade por owner/conta, cancela a varredura atual e aguarda a liberação normal do gate, sem apagar intents ou ignorar referências. Após a última operação prioritária, a manutenção pendente é retomada, desde que a conta configurada continue sendo a mesma. A manutenção compartilha uma prova remota de referências por lote de intents, com cache limitado de mensagens de até quatro pools, em vez de reler toda a biblioteca para cada arquivo. Exclusões explícitas e confirmações necessárias à integridade continuam usando suas proteções.

A reserva compartilhada usa localizadores de catálogos guardados com DPAPI por instalação/conta/canais, mas recarrega o catálogo remoto antes de decidir capacidade, identidade e membros. Destinos comprovadamente removidos são fechados e deixam de ser escolhidos. Intents de criação sem confirmação exigem reconciliação para evitar posts duplicados. Um snapshot operacional do journal em `StorageJournalCache`, protegido pelo DPAPI e vinculado à conta, owner, canais e thread técnica, conserva catálogos, referências, intents, fences e claims já autenticados. Toda utilização consulta primeiro os eventos novos no servidor e pagina até o frontier conhecido, inclusive quando há mais de cem eventos novos. Eventos migrados com ordem lógica antiga exigem replay completo. Snapshot ausente, inválido ou de outro índice causa leitura completa. Escritas de catálogo e provas de GC continuam remotas; o snapshot não autoriza limpeza. Sem cache operacional válido, a leitura completa pode aquecer durante o envio, fora do gate enquanto aguarda a rede. Anexos técnicos pequenos são lidos com até oito leitores e até 32 MiB de documentos materializados em RAM; documentos grandes permanecem sequenciais. Uma substituição verifica reservas de edição antes de transmitir e revalida o conteúdo antes de publicar. Claims inativos deste owner são recuperados nesse caminho; claims estrangeiros não expiram por idade.

Uploads dedicados criam o post com somente o chunk 0 e enviam os demais em batches de até dez. Shared começa com controle sem arquivo e agrega attachments de arquivos/roles diferentes. Cada attachment mantém ORGAESGC e o `ChunkCount` global daquele arquivo/role. A resposta inteira é validada; checkpoints são atômicos por arquivo, com recibo remoto para recuperar distribuição parcialmente salva entre participantes. A retomada usa chunks confirmados; o progresso visual usa bytes lógicos transmitidos. Checkpoints antigos sem `payloadLayoutVersion` continuam unitários; dedicados multi-attachment usam 2 e compartilhados usam 3. O download deduplica mensagens e seleciona pelo attachmentId. `chunkRefs` ou layout declarado inválido não vira legado silenciosamente.

O upload da biblioteca mantém um contexto de índice em `AppRegistry.UploadBatch`: cada índice de pasta usado pelo lote é desarquivado uma vez, recebe os metadados individuais e só é arquivado ao encerrar o último lote ativo. `SharedStorageManager.HoldWritesAsync` mantém também a thread técnica do journal aberta junto com os pools, inclusive durante a finalização de um upload individual/retomado. Gravar planos, recibos, claims e referências não alterna archive/unarchive por registro; o último lease encerra a escrita e arquiva a thread. Cancelamento e falha liberam os contextos. A reconciliação não arquiva índices/pools que estejam em uso. Seriais são publicados ao fim; a reconciliação de reservas confirmadas segue em segundo plano, cancelável por novas operações interativas, sem prender o término visual do lote. Os arquivos continuam independentes por fileId/encryption/refs mesmo quando compartilham o post físico. Rate limits e tratamento de HTTP 429 permanecem obrigatórios.

O agendamento mantém até 16 arquivos nas vagas de execução do lote, incluindo preparação, transmissão, miniaturas e publicação. A geração da prévia 480p libera temporariamente essa vaga e aparece como processamento; antes de enviar a prévia ou continuar a publicação, o vídeo recupera uma vaga. Assim, outros arquivos continuam enquanto o codec trabalha, sem aumentar o limite de uploads em execução ou o orçamento de memória. Cada arquivo aparece como `Aguardando upload` antes do início da transmissão, inclusive enquanto o app verifica partes já confirmadas de uma retomada. A interface mantém a contagem de concluídos a partir das linhas confirmadas. Após enviar os payloads, o arquivo aparece em finalização até publicar os metadados e gravar o checkpoint. A conclusão visual independe do arquivamento posterior da thread. Os originais são admitidos por pool. Encerrar a etapa original do grupo atual permite admitir o próximo pool, enquanto as prévias anteriores continuam pendentes; a operação só termina depois de concluir também essas prévias e suas publicações. Originais shared de uma parte usam até 16 descritores; multipart/dedicados respeitam a configuração de arquivos simultâneos, de 1 a 16. As partes desses arquivos compartilham o mesmo gate de transmissão, limitado a 16; partes não criam outras 16 operações de arquivo. Imagens shared geram a miniatura enquanto o original é preparado e enviam os dois anexos no mesmo multipart. O agrupador admite esse par como unidade, preservando contextos criptográficos e checkpoints independentes. Uma miniatura já confirmada não é reenviada na retomada. Depois de confirmar os originais, a vaga de original é liberada antes da publicação, mas o trabalho só chega a 100% após publicar o arquivo. O batcher conhece os produtores futuros aguardando admissão; os limites não ampliam workers HTTP nem o orçamento de RAM. A preparação da biblioteca já anuncia prioridade interativa antes de aguardar o índice. Novos checkpoints shared são gravados depois de receber identidade, criptografia e reserva pendente, evitando uma primeira gravação incompleta e sua substituição imediata. Buffers criptográficos de miniaturas são preparados somente na transmissão.

Cada arquivo concluído e pasta criada é publicado sobre a coleção local atual, sem substituir por uma cópia capturada no começo do lote. Durante o upload, o bridge envia somente a entrada alterada por `_onAppsBatch`, que faz upsert por identidade, sem apagar os cards de uma conclusão mais recente quando um callback atrasado chega. A coleção muda imediatamente; publicações próximas compartilham uma atualização visual agendada em 100 ms, evitando ordenar e percorrer a biblioteca inteira para cada arquivo concluído. Com Configurações ou o editor em primeiro plano, essa atualização visual aguarda o retorno à biblioteca. O encerramento do lote também usa publicação incremental. Movimentações para a Lixeira atualizam somente as entradas afetadas; exclusões definitivas removem suas identidades por `_onAppsRemoved`. Esses callbacks preservam a coleção carregada ao navegar para outra pasta durante a operação. Reconciliações explícitas continuam substituindo a coleção correspondente. O resumo lateral conserva o último agregado completo como base. Cada arquivo publicado acrescenta imediatamente seu tamanho e sua contagem ao agregado local persistido, sem consultar novamente o Discord; uma nova versão acrescenta o conteúdo novo, preservando os bytes do histórico e a contagem de arquivos. Leituras de totais iniciadas antes dessas conclusões não substituem um agregado local mais recente. Ao sincronizar os seriais no fim da operação, o total completo volta a ser conferido. O renderer reconcilia cards e linhas por identidade e conteúdo: itens inalterados mantêm seus elementos, miniaturas e seleção; inclusões, alterações e remoções efetivas afetam somente os itens correspondentes. A visualização inativa é limpa para não duplicar elementos ou seleção entre grade e lista.

Os chunks de upload são lidos por faixa e cifrados somente em RAM, inclusive em arquivos pequenos, retomadas criptografadas, miniaturas, imagens Markdown e uploads do sincronizador. `UploadMemoryCoordinator` usa o pool global de `RamUploadBudget`; não há ciphertext temporário no SSD. O upload da biblioteca lê o original diretamente, sem copiá-lo para o TEMP do Windows. Faststart e miniaturas permanecem sem mídia intermediária. Somente a prévia 480p convertida pode ser gravada temporariamente, em pasta oculta ao lado do original, conforme a seção de vídeo. Retomadas plaintext antigas preparam cada faixa em RAM. Snapshots da sincronização, checkpoints, cache de miniaturas e arquivos de destino/intermediários plaintext de download mantêm suas finalidades operacionais.

`AppMemoryBudget` aplica um limite Windows de 1.000.000.000 bytes de memória privada comprometida ao processo C# e a cada auxiliar de mídia explicitamente registrado. A política de criação permite que filhos saiam desse Job Object; os processos do WebView2 ficam fora dele, evitando que a soma do navegador provoque falhas de alocação nativa quando o executável ainda está abaixo do limite. O heap gerenciado tem teto de 512 MiB. Antes de preparar um lote, a admissão considera memória atual de C#/auxiliar, buffers existentes e reservas de outros uploads/downloads, com alvos de 800 MiB totais e 448 MiB gerenciados. Há espaço reservado para dois buffers plaintext e aproximadamente 400 MiB de ciphertext, reduzido quando necessário. Até 160 partes pequenas podem ocupar as vagas de chunks, mas a admissão é por bytes, não autorização para alocar 160 chunks de 20 MiB. Sob pressão, novos trabalhos aguardam de forma cancelável. Esse limite controla memória privada comprometida, não memória compartilhada de DLLs/GPU, cache de disco do Windows ou paginação do sistema.

O plaintext é zerado ao voltar ao pool. No upload agrupado sob demanda, o ciphertext é zerado e devolvido logo após transmitir o anexo, sem esperar o ACK da mensagem. Durante a espera ficam somente descritores, nonce e um digest de integridade por chunk. Um retry relê a faixa e regenera os mesmos bytes cifrados apenas após verificar plaintext, chave derivada e contexto autenticado; uma alteração é recusada antes de reutilizar o nonce. O pool limitado é compartilhado e reutilizado entre transferências, sem coleta completa bloqueante ao terminar cada arquivo. Buffers livres podem ser descartados sob pressão. Os caminhos unitários e de partes já preparadas conservam sua retenção anterior até sucesso/falha/cancelamento. Nenhum caminho cria um buffer para o multipart inteiro.

Miniaturas aguardando memória têm prioridade de admissão em `RamUploadBudget`: novas reservas de chunks aguardam enquanto envios existentes liberam espaço para a geração. A espera por essa memória continua assíncrona e cancelável, sem ser confundida com timeout do codec. Após a admissão, uma execução de codec isolado de miniatura tem limite de 30 segundos; falha mantém o original e permite o tratamento não fatal da miniatura. Imagens geradas permanecem em RAM. O teto global de 1 GB e a política separada de vídeo 480p permanecem vigentes.

Configurações > Uploads inclui `Forçar 16 workers (RAM até 1 GB)`, desativado por padrão e persistido em `forceUploadParallelism`. Ativo, oferece até 16 workers globais de transmissão sem redução dinâmica por vazão, mantendo arquivos simultâneos, memória, rate limits e limites de attachments. Nos uploads agrupados, `UploadBodySlot` adquire a vaga antes de enviar a requisição e a devolve ao terminar os anexos; uma confirmação lenta não ocupa essa vaga. Até 64 mensagens podem aguardar trabalho ou confirmação, com backpressure global. `UploadConcurrencyRegistry` reconfigura imediatamente os gates ativos da biblioteca, retomadas e sincronização; não é necessário reiniciar a transferência. Requisições em andamento terminam normalmente, e a política nova vale para novas admissões. Desativar restaura o limite adaptativo. A interface destaca o botão, exibe 16 e desativa o controle de partes enquanto ele estiver ativo. Dezesseis workers não significam dezesseis buffers de 200 MiB: cada transmissão usa somente o buffer do anexo atual.

`ForumUploader.MultiAttachment` produz descritores de lotes de dez anexos, com `Channel` de capacidade um e teto global de 64 mensagens pendentes. Cada conteúdo HTTP prepara um anexo por vez em RAM enquanto outros requests transmitem; dois workers de leitura/cifra alimentam os workers de transmissão. A admissão por bytes ocorre por anexo, não por mensagem de 200 MiB. Ao concluir o corpo útil, os buffers e a vaga de transmissão ficam disponíveis para sucessores enquanto a resposta anterior continua pendente. O agrupamento HTTP não altera tamanho, índice, nonce, salt, contexto ou referências lógicas dos chunks. Os caminhos de partes materializadas permanecem disponíveis para compatibilidade e transportes unitários. Disco mais lento que a rede, pressão externa de memória e esperas impostas pela API ainda podem interromper a transmissão: não existe garantia física de rede ocupada 100% do tempo.

No modo adaptativo, `UploadThreads` é dividido entre arquivos ativos, e `AdaptiveUploadGate` pode reduzir/reabrir vagas conforme amostras de vazão agregada. Todos os índices de uma mensagem nova são salvos juntos no checkpoint após validar a resposta, permitindo retomar sem reenviar chunks confirmados. A recuperação de posts órfãos exige estado local e origem disponíveis, sem inventar nome, pasta, criptografia ou referências, e não inicia outra retomada silenciosa. Falhas transitórias, HTTP 520/5xx e desconexão mantêm retry cancelável; HTTP 429 respeita o bucket do Discord. Durante uma transferência, esse contexto também cobre chamadas de índice/metadados que permitem repetição segura. Timeout de transporte sem cancelamento solicitado aguarda nova tentativa; cancelamento explícito continua interrompendo a operação. Requisições com resultado desconhecido e repetição proibida preservam sua estratégia de reconciliação, sem duplicar POSTs cegamente. Uma espera isolada não substitui o progresso enquanto outra requisição transmite. O thread e os chunks confirmados são preservados. Mensagens de status não são persistidas; o coletor temporário conserva somente sinais técnicos limitados, conforme a seção de diagnóstico.

Depois de carregar a biblioteca na interface, o desktop pergunta uma vez por sessão se o usuário deseja retomar transferências locais interrompidas, excluindo as do sincronizador. Não inicia automaticamente por `autoResumeTransfers`, ainda aceito como configuração legada. Uploads retomados usam `RunUploadQueueAsync`: painel do lote, velocidade, estimativa, pausa, cancelamento e publicação incremental. Reservas e partes confirmadas são revalidadas. Se um destino vazio tiver sido removido, o checkpoint sem anexos confirmados reserva outro pool sem mudar fileId, versão, criptografia, checksums ou origem. Cancelar o lote também retira checkpoints de arquivos ainda na fila e encerra o estado visual. A intenção de limpeza é gravada atomicamente em `StorageCleanupOutbox`, separada por conta, antes de retirar o checkpoint; uma manutenção importa essa intenção para o journal e faz a limpeza remota posteriormente. Threads dedicadas sem referências são removidas. Em pools com outros arquivos, somente os anexos do upload cancelado são retirados; pools que ficam vazios passam pela auditoria autenticada de referências e controle antes de excluir o post. As pendências continuam duráveis caso rede, referências ou operações ativas impeçam concluir a limpeza. Isso evita que a resposta ao cancelamento espere pela varredura histórica ou pelo GC. Downloads retomados usam o metadata salvo no checkpoint mesmo fora da pasta aberta e preservam métricas e cancelamento. A conclusão não redefine a navegação para a raiz.

As vagas de rede limitam transmissões de requisições/batches, não attachments nem respostas pendentes. Duas faixas podem ser lidas/cifradas simultaneamente no processo, independentemente dos workers de rede. O multipart utiliza streams individuais e nunca um buffer de 200 MiB. Rejeições específicas de quantidade/tamanho reduzem o agrupamento e reproduzem os payloads cifrados; outros HTTP 400 não recebem esse retry. Cada tentativa readquire sua vaga de transmissão, e backoff/429 não mantém buffers de anexo. Falha ou cancelamento interrompe também o produtor e limpa os descritores ainda não enviados. Abertura, leitura, cifra, preparação de upload e gravação/verificação de download executam fora do Dispatcher WPF, evitando bloquear a interface enquanto o armazenamento responde.

O progresso individual avança por bytes lógicos, não por chunks confirmados. Preparação e metadata não somam porcentagem. Imagens shared usam 0–99% para a transmissão conjunta do original e da miniatura, sem estágio separado de envio da miniatura. O original determina o avanço visual, enquanto bytes da miniatura entram no total e na velocidade. Vídeos com prévia ativada usam 0–80% para o original, 80–90% para gerar a prévia e 90–99% para enviá-la; sem prévia, o original vai a 99%. Todos chegam a 100% após publicar o arquivo. ACK pendente e metadata mostram `Concluindo`. A barra do lote pondera cada arquivo pelo tamanho do original. `UploadWireProgressStream` e `UploadByteProgress` separam bytes transmitidos/retries do avanço lógico. Downloads usam uma janela móvel de 60 segundos, e verificação não simula novos bytes de rede. A velocidade exibida usa os bytes transmitidos durante a atividade de rede. A ETA usa uma janela de até 60 segundos de tempo decorrido e avanço lógico, incluindo as esperas entre envios. Em lotes de upload, considera também a cadência de arquivos concluídos, incluindo sua publicação, e mostra a maior das duas estimativas disponíveis. A ETA aparece após haver uma amostra utilizável, some durante pausa/espera e ao terminar, e reinicia sua amostragem ao retomar.

### Download, integridade e compatibilidade

O início de um download usa as referências do metadata do arquivo e publica sua referência de leitura no índice técnico, sem reconstruir o histórico global de armazenamento nem depender de `StorageJournalCache`. O mapping técnico já conhecido é reutilizado. As restrições de exclusão já carregadas continuam sendo respeitadas; uma exclusão remota já em andamento pode tornar os anexos indisponíveis, e o erro conserva a retomada. Reconciliação e limpeza continuam lendo o journal e comprovando as referências antes de remover conteúdo. Prévias conservam a preparação anterior de leitura.

Downloads cifrados reutilizam buffers de ciphertext e plaintext com tamanho exato do pool global. A reserva usa a contabilização desse pool, sem somar novamente seus arrays como memória externa nem criar dois arrays grandes por chunk. Os buffers só voltam ao pool depois da autenticação e da escrita, são zerados ao retornar e não ficam retidos pelos checkpoints. A fila conserva buffers livres enquanto há payloads ativos e os descarta sob pressão depois de drenar essas reservas. Os limites globais de RAM, workers, GCM, checksums e retomada continuam valendo.

Uploads novos da biblioteca, edição/cópia e sincronização incluem `checksums` V1 nos metadados cifrados: SHA-256 do conteúdo plaintext completo e de cada chunk lógico. `StreamingUploadChecksums` inicia a leitura sequencial do manifesto em paralelo à transmissão, com buffer de até 1 MiB admitido no orçamento global; o primeiro envio não espera a leitura integral. Separadamente, cada parte calcula o hash do plaintext que será cifrado e o salva no checkpoint antes de transmitir, sem gravar mídia intermediária. O checkpoint local usa `uploadChecksumPending` enquanto o manifesto estiver parcial, conservando as provas das partes preparadas, inclusive quando uma resposta se perde. Antes de publicar os metadados, o app compara todas essas provas com o manifesto completo e retira o marcador; divergência impede a publicação. Uma retomada confere também o prefixo já enviado durante essa leitura paralela, sem refazer seus uploads. Checkpoints antigos sem manifesto continuam com o contrato legado. O cálculo total continua sendo uma leitura adicional da origem, mas não uma etapa bloqueante antes da rede. No MP4 faststart, os hashes correspondem ao stream virtual efetivamente enviado, não aos bytes físicos anteriores ao remapeamento. O SHA-256 completo aparece em `Ver informações`. O contrato interoperável está em [Download e integridade](#download-integridade-e-compatibilidade).

No download, o app verifica o hash do chunk após autenticar/decifrar em RAM e antes de gravar plaintext diretamente no intervalo correspondente de um único `.part`, ao lado do destino. Em volumes com suporte a arquivos esparsos, o parcial recebe esse atributo antes das escritas: uma parte recebida fora de ordem não obriga o Windows a gravar zeros nos intervalos ainda pendentes. Esses intervalos continuam retornando zeros e não contam como partes baixadas; somente bytes recebidos e autenticados são confirmados. Volumes sem esse suporte mantêm a alocação convencional. Chunks legados sem criptografia fluem com buffer de 1 MiB e hash incremental. O arquivo não é montado nem copiado ao finalizar: uma leitura sequencial confere as regiões e o SHA-256 completo, quando declarado, seguida de flush e renomeação no mesmo volume. O destino anterior só é substituído após validação. Nenhum checksum inválido pode ser ignorado.

Quando o metadata contém as referências das partes, o início depende somente das primeiras dez. `PartDiscovery` resolve as seguintes em janelas de até cem, com uma janela enfileirada, durante o download; IDs de mensagem repetidos são deduplicados e `attachmentId` continua obrigatório para `chunkRefs`. A fila não espera o término de um lote ou seus checkpoints para admitir as partes da próxima janela. Há até 64 trabalhos pendentes, separados das vagas de rede e sem reter plaintext/ciphertext após a escrita. O número configurado de workers e o orçamento global de RAM continuam limitando os payloads. Offsets são calculados pelos tamanhos reais dos anexos, inclusive em layouts legados com tamanhos variáveis, e publicados sem modificar regiões já entregues aos workers. Partes novas ainda não resolvidas podem ficar no checkpoint sem `Offset` e com `logicalSizeBytes = -1`; não são confirmadas até a gravação autenticada. A retomada verifica os limites e o hash local antes de reutilizar cada região. Arquivos antigos sem referências utilizáveis mantêm a recuperação por batch/histórico; esse fallback ainda precisa localizar o conjunto de partes.

Os checkpoints de download usam `downloadCheckpointVersion: 1`, identidade do conteúdo/versão, caminhos parcial/final, offsets, tamanhos lógicos e SHA-256 local por região. `TransferStateRepository` continua sendo a única persistência. Dados são sincronizados fisicamente antes de salvar grupos de até quatro conclusões e ao drenar os workers. A vaga de rede é liberada depois da escrita/autenticação da parte e da liberação dos buffers, antes de aguardar o checkpoint; novas partes podem ser recebidas durante essa persistência, sem aumentar workers nem orçamento de RAM. A conclusão continua aguardando todos os checkpoints e a verificação final. Os valores transferidos usam ponto e uma casa decimal para KB/MB/GB/TB em todos os callbacks, sem alternar a precisão. Na retomada, somente regiões presentes e com hash válido são reaproveitadas; ausentes, truncadas, alteradas ou não confirmadas voltam à fila. Erros de download preservam estado pausado; cancelamento sem limpeza também preserva a retomada. Cancelamento com limpeza remove apenas o parcial identificado pela transferência, depois de fechar as escritas. Uploads mantêm seus estados e sua política anterior.

Uma transferência recuperável da mesma identidade e destino é reutilizada; um destino em uso recusa outro escritor. A identidade inclui versão, referências, criptografia e checksums, sem depender apenas do nome. Uma marca persistida de finalização com SHA-256 permite reconhecer o arquivo já renomeado após uma interrupção, inclusive sem consultar a rede. Checkpoints antigos podem importar arquivos plaintext por região apenas quando há hash verificável; sem ele, a parte é baixada novamente. Arquivos antigos comprovadamente pertencentes à transferência só são removidos depois de sua substituição durável. Não há exclusão recursiva de diretórios legados. A especificação local e os limites de validação estão em [Download e integridade](#download-integridade-e-compatibilidade), e a compatibilidade em [Download, integridade e compatibilidade](#download-integridade-e-compatibilidade).

Os hashes acompanham cache SQLite, metadados completos, cópias de organização e snapshots de versões, sem alterar OSER ou ORGAESGC. Dados antigos sem `checksums`, inclusive checkpoints de upload já parcialmente confirmados antes desta implementação, mantêm as validações anteriores; não recebem hashes inventados a partir de uma origem atual possivelmente diferente. Não existe migração ou download automático da conta. Prévias e miniaturas mantêm a autenticação GCM existente; este manifesto descreve somente o conteúdo principal de cada versão.

Exceções temporárias de rede, incluindo tarefas de conexão do Discord observadas pelo handler global, continuam registradas no diagnóstico, mas não abrem diálogos genéricos. A classificação considera também exceções de transporte sem status HTTP e agregações compostas somente por falhas transitórias. Erros de permissão, autenticação criptográfica e integridade mantêm seu tratamento específico.

O coletor temporário descrito abaixo é o destino principal de `AppLogger` enquanto estiver ativo. Ele conserva eventos técnicos limitados, sem as mensagens de status, argumentos ou dados dos arquivos. Fora desse modo, o logger anterior continua sem persistir INFO/DEBUG/WARN e conserva somente os erros previstos. Logs antigos não são removidos automaticamente.

Durante um download, falhas de conexão/TLS, timeouts de transporte e respostas temporárias de rede mantêm a operação ativa com `Aguardando rede...`. Esse estado também acompanha as esperas do Discord durante a preparação do download e o registro da leitura compartilhada. O recebimento dos headers e cada leitura do conteúdo têm limite de 30 segundos sem resposta; esse limite é de inatividade, não da duração total do arquivo. Ao voltar a conexão, o app repete a tentativa e preserva as partes já confirmadas. Pausa e cancelamento explícitos continuam funcionando durante a espera. Timeouts de transporte não consomem as tentativas destinadas a integridade.

Para payloads criptografados, cada tentativa recebe o ciphertext em RAM, valida o envelope e a tag GCM, confere o checksum quando declarado e só então grava o plaintext retomável. Falhas temporárias de rede durante o download aguardam e repetem a parte até a conexão voltar. Falhas de estrutura, autenticação ou checksum descartam a tentativa suspeita e fazem no máximo três downloads completos por payload. Após reconstruir o arquivo, o tamanho plaintext é comparado com `sizeBytes` do metadata. Arquivos com manifesto também exigem todos os hashes válidos antes de concluir.

Uma falha de autenticação nunca entrega plaintext. Em modo personalizado, a interface informa que a chave configurada pode estar incorreta. Quando a autenticação passa, mas apenas o tamanho do metadata diverge, o app preserva o arquivo validado e oferece `Abrir mesmo assim` em um diálogo nativo.

Entradas legadas sem `encryption` continuam acessíveis por download direto. O cache de previews usa `EncryptedPreviewCache`, separado do envelope remoto `ORGAESGC`; cache antigo em claro é descartado na primeira abertura da versão atual e recriado quando solicitado. Novos downloads criptografados não criam cópia ciphertext no disco: cada parte é autenticada em RAM antes de gravar plaintext retomável, e retries descartam a tentativa inválida. A reprodução progressiva também autentica cada chunk em RAM antes de expô-lo ao player.

## Diagnóstico temporário de desenvolvimento

`Organessonium.csproj` seleciona `DesktopEntryPoint` como entrada STA. Ela conecta os observers antes de construir `App`, carregar seus recursos ou iniciar o WPF. A criação da pasta, recuperação de sessões e gravação acontecem em outra thread, sem fazer a janela aguardar o armazenamento. O auxiliar `--media-preview-worker` não inicia outro coletor. Não há serviço Windows, executável adicional, hook global de teclado/mouse, telemetria externa ou inspeção de outros aplicativos.

O módulo está em `Services/Diagnostics`: `DevelopmentDiagnostics` é a fachada opcional; `DiagnosticSession` mantém sessão, fila, persistência e vigilância; `DiagnosticWebView` conecta eventos do navegador; `DiagnosticLabels` limita rótulos a valores técnicos conhecidos. Remover/desativar o módulo não muda resultados, retries, cancelamentos, paralelismo ou tratamento de exceções das operações observadas.

O diretório é fixo e anterior às configurações: `%APPDATA%\OrganessoniumData\Logs\Diagnostics\<sessão>`. Isso também vale quando a pasta operacional do banco foi personalizada. Configurações mostra `Diagnóstico temporário`, seu estado e o caminho da sessão. Os arquivos `trace-0000.jsonl`, `trace-0001.jsonl` etc. usam JSON UTF-8 sem BOM, uma linha por evento. Para análise durante execução, o leitor precisa permitir compartilhamento de leitura/escrita e rotação; uma última linha ainda incompleta deve ser ignorada até a próxima leitura.

Cada evento inclui UTC, tempo monotônico desde o início, sequência local, tipo, área, thread gerenciada, ID local da operação e dados técnicos. A sessão inicial informa protocolo 1, PID, versão do assembly e runtime. Operações têm início/fim, ID local/pai e duração. A instrumentação cobre:

- Exceções gerenciadas lançadas, erros enviados ao logger, falhas não tratadas do domínio, exceções do Dispatcher e tasks não observadas. Registra tipo, HResult e até quatro causas com 16 frames cada, incluindo método, linha disponível e offset IL. Não grava `Exception.Message`, `ToString`, `Data`, nomes/caminhos de arquivos, valores dos argumentos, chaves ou tokens.
- Despacho de comandos do bridge, trabalhos assíncronos e callbacks relevantes da UI. Rótulos desconhecidos viram `unknownCommand`/`application`, nunca cópias de entradas arbitrárias.
- Tentativas REST do `DiscordApiClient`, com rota anonimizada, tempo total incluindo esperas e status HTTP. IDs, host, query, headers, token e corpo não são gravados; CDN e stderr de auxiliares não recebem captura de conteúdo.
- Despacho de cada batch shared, em `upload.batch`, com quantidade de anexos, tempo de agregação e presença de produtores pendentes. Não inclui IDs, nomes, conteúdo ou chaves.
- Navegação, tipo/motivo/código de falha de processo WebView2 e erros/rejeições JavaScript. JavaScript conserva somente classe do erro e linha/coluna, não sua mensagem ou stack textual.
- A cada dois segundos: memória privada comprometida e working set total do executável, working set privado do executável (`privateWorkingSetBytes`), heap/commit gerenciado, memória do backend (`jobCommittedBytes`) e do WebView2 em campo separado (`webViewPrivateBytes`), tempo acumulado de CPU, threads, fila do ThreadPool, contadores GC, exceções observadas, eventos descartados e até 16 operações em andamento. Não inicializa nem altera o orçamento de memória para obter métricas.

Uma thread de vigilância separada da escrita posta no máximo um pulso pendente no Dispatcher. Cinco segundos sem resposta produzem `ui.stalled`; a resposta posterior produz `ui.recovered`. O JavaScript envia um pulso a cada dois segundos; páginas visíveis sem resposta por 12 segundos produzem o mesmo sinal na área `javascript`. Uma navegação sem primeiro pulso recebe `webview.heartbeatMissing`. Uma página oculta não é classificada como congelada pela ausência do timer. Os observers permanecem ativos ao ocultar a janela na bandeja; são liberados na recuperação do WebView2 ou no encerramento real. Esses eventos indicam tempo sem resposta, não estabelecem a causa nem tratam trabalho demorado como uma falha fatal.

`exception.observed` é uma notificação first-chance, anterior à escolha do `catch`. Ela também ocorre em comportamentos normais e não prova que houve crash. Há amostragem de até 16 dessas notificações por intervalo; erros explícitos continuam indo pela via prioritária. Eventos repetitivos são limitados por rótulo a um por intervalo. A fila admite 512 eventos com reserva de 64 vagas para erros, além de até oito pedidos limitados de flush; sob saturação, erros recentes substituem registros antigos e o descarte é contabilizado. Até 128 descritores de operações são retidos. Não há buffers de mídia, dump de memória ou plaintext de arquivos nesse módulo.

O writer descarrega periodicamente, faz flush limitado na falha terminal/saída e rotaciona quatro arquivos de aproximadamente 4 MiB por sessão. A manutenção conserva a sessão atual e até três sessões inativas anteriores, preservando sessões de processos ainda vivos. Apaga somente traces/marcadores reconhecidos de pastas geradas pelo módulo, sem seguir reparse points nem remover conteúdo inesperado. Os `.log` anteriores permanecem intactos. A retenção comum fica perto de 64 MiB, além de sessões simultâneas ainda ativas; arquivos antigos podem ser removidos pela rotação, portanto copie a sessão relevante antes de muitos reinícios.

`active.json` guarda somente PID e horário de criação do processo. A saída normal, depois de drenar o writer, remove esse marcador. Na próxima abertura, um marcador sem processo correspondente produz `previous.uncleanExit` referenciando a sessão anterior. Isso pode significar crash, encerramento pelo Gerenciador de Tarefas ou desligamento abrupto, não necessariamente bug. Um término nativo, `FailFast`, stack overflow, falta extrema de memória ou queda de energia pode impedir os últimos registros; o coletor não promete capturar um stack nativo nem impedir a falha. Logs descrevem o que foi observado, não autorizam alterações especulativas dos fluxos existentes.

Para desativar sem recompilar, inicie o processo com `ORGANESSONIUM_DIAGNOSTICS=0`. Configurações então informa o estado desativado. Para remover em outra versão, siga `DIAGNOSTICS-TEMP-001` em [Download, integridade e compatibilidade](#download-integridade-e-compatibilidade); a entrada WPF gerada pode voltar a ser usada e os poucos hooks saem junto do módulo. O logger anterior permanece disponível como fallback quando a coleta estiver desativada/indisponível. Seus arquivos podem conter mensagens/caminhos legados e devem ser revisados antes de compartilhar.

Semântica da notificação: [AppDomain.FirstChanceException](https://learn.microsoft.com/en-us/dotnet/api/system.appdomain.firstchanceexception?view=net-10.0).

## Reprodução de vídeo e faststart

Downloads de arquivos usam 0–99% para recebimento/gravação direta e mostram `Verificando integridade do arquivo...` na conferência final, sem reservar 20% para uma montagem inexistente. Chegam a 100% depois da renomeação. A velocidade usa bytes novos de rede, separados dos bytes recuperados do checkpoint; a verificação não simula tráfego. O campo legado `DownloadProgress.Assembling` apenas sinaliza essa fase final aos consumidores existentes. Chunks criptografados continuam autenticados integralmente em RAM; não existe etapa `.encrypted` em disco. A admissão global, o limite de payload de 64 MiB, `DownloadThreads`, `MaxParallelDownloads` e o teto de RAM permanecem iguais. O destino de download continua plaintext e exige proteção local pelo usuário; o cache de prévias é cifrado separadamente.

Configurações > Uploads oferece `Gerar prévias 480p dos vídeos`, persistido em `generateVideoPreviews` e ativado por padrão. Desativar não remove miniaturas nem prévias já existentes e não desativa a reprodução progressiva do original. A opção vale para novos lotes e retomadas iniciadas depois da mudança; o lote em andamento mantém a preferência inicial; a preferência de qualidade de reprodução é independente. No painel, borda e barras/círculos de upload são neutros. Passar o mouse sobre o progresso de um arquivo ativo ou na fila revela X, que cancela somente esse arquivo; os demais continuam. Após publicar um arquivo, sua entrada aparece imediatamente na listagem da pasta atual, e encerrar o lote não troca a coleção por apenas a raiz.

O player existente lê chunks sob demanda por `VideoStreamSession`, sem reconstruir o vídeo inteiro, criar mídia temporária ou persistir chunks no SSD. O índice usa os tamanhos plaintext reais dos attachments, com prefix sums e busca binária: arquivos antigos de 10 MiB, novos de 20 MiB, partes finais menores e tamanhos misturados não dependem do limite atual do uploader. A abertura entrega a URL ao player sem esperar o download de aquecimento; a primeira faixa solicitada inicia a leitura. Muitas mensagens referenciadas são resolvidas por páginas de até 100 mensagens usando `around`, retendo somente IDs exatos pedidos e caindo para consultas individuais se necessário. Isso evita uma chamada por chunk ao abrir vídeos grandes, sem supor tamanhos constantes. O endpoint segue [Get Channel Messages](https://docs.discord.com/developers/resources/message#get-channel-messages). MP4 com `moov` no final permite leitura direta da região final e seek sem baixar todas as partes intermediárias. Não há migração ou reenvio dos vídeos já armazenados. Latência, limites da API e autenticação integral do primeiro chunk ainda condicionam o início; não existe garantia de início instantâneo em qualquer rede.

O player só declara MIME em `<source>` quando o runtime informa suporte. Assim, `video/quicktime` não impede a detecção de MOV H.264 compatível. Falha de codec no original solicita a prévia 480p quando disponível; MOV/HEVC ou outro codec sem suporte e sem prévia continua sujeito às capacidades do WebView2. Volume e mute são persistidos em `localStorage`, chave `video-volume`, e restaurados em cada player. O botão de fechar fica à esquerda do cabeçalho da prévia, fora das regiões nativas de arraste. O cabeçalho usa a altura e os recuos informados pela barra nativa para alinhar os controles; uma região vazia remove a área de arraste anterior. Enquanto ela estiver aberta, inclusive em tela inteira, o fechamento nativo da janela fecha somente a prévia.

Prévia e miniaturas iniciam o trabalho de disco/decodificação fora do Dispatcher. Ao trocar ou fechar uma foto, o pedido anterior é cancelado; respostas de imagem/vídeo com requestId antigo não substituem o item atual. Cópias para cache são concluídas por troca atômica, sem publicar um arquivo parcial. Falhas de processo GPU/utility são registradas sem recriar toda a interface, pois o runtime as recupera automaticamente; a política segue [process-related events](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-related-events). Falhas do browser/renderer agendam a recuperação no Dispatcher depois do retorno do callback nativo, sem descartar o controle dentro desse evento. Um encerramento já iniciado impede a recriação. Essa ordem respeita o [modelo de threading/reentrância do WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/threading-model#reentrancy). Isso não estabelece a causa de todas as falhas nativas nem promete eliminar travamentos de drivers/runtime.

Os cards usam `content-visibility: auto` para permitir que o navegador organize layout e pintura. Miniaturas são solicitadas pela área visível, com margem de 180 px acima e uma linha adicional abaixo. Depois de carregadas, suas imagens, fontes e cards permanecem montados enquanto a pasta estiver aberta, inclusive fora da tela. Retornar a uma região já visitada reutiliza os mesmos elementos, sem substituí-los por ícones nem solicitar outra miniatura. Atualizar os dados de um card também preserva sua imagem quando o payload e a referência da miniatura continuam iguais. Navegar para outra pasta ou remover um arquivo libera os elementos correspondentes. O cache JavaScript mantém até 128 URLs curtas; essa política não remove imagens que continuam nos cards. O cache C# também usa LRU com até 128 URLs e recupera endereços do cache cifrado sem Discord. Conteúdo de imagens não é convertido para Base64 na ponte.

Configurações > Prévias inclui `Chunks de vídeo antecipados`, chave `videoPrefetchChunks`, padrão 1 e intervalo de 0 a 6. Zero desativa antecipação, mantendo as leituras necessárias. O valor vale para sessões novas. Durante reprodução, o app mantém uma janela limitada de chunks, deduplica downloads simultâneos e cancela prefetch obsoleto em seek, pausa ou fechamento. O cache plaintext tem teto de 192 MiB e o player recusa chunks individuais acima de 64 MiB; esses limites não alteram o protocolo de upload de 20 MiB. Falhas temporárias têm retry cancelável; falha definitiva aparece no fallback do player. Download completo, checkpoints e cancelamento continuam independentes da reprodução.

O download de cada chunk do player passa pela admissão global de RAM antes de iniciar a CDN ou alocar ciphertext/plaintext, considerando a capacidade arredondada do pool cifrado. Espera por memória é assíncrona e cancelável; fechar a sessão desliga esse pool, mesmo que uma resposta COM ainda retenha a sessão. Antes de abrir um decoder com a memória agregada acima de 544 MiB, o controller descarta apenas caches ociosos de RAM e recolhe objetos liberados fora do Dispatcher. `VideoPlaybackMemoryGuard` verifica a memória agregada a cada 100 ms enquanto existem sessões de vídeo. A partir de 672 MiB, essa mesma recuperação ocorre no máximo uma vez a cada cinco segundos, sem retirar a fonte, pausar, trocar a qualidade ou descartar os chunks atuais. Somente se a memória continuar em 864 MiB ou mais após a recuperação o controller cancela e retira os recursos e a UI descarrega o decoder. Depois de drenar os trabalhos, a UI solicita uma única tentativa da prévia 480p já existente, preservando a posição e o estado de reprodução. Sem essa prévia, se ela falhar ou se continuar havendo pressão crítica, o painel informa a interrupção e mantém as ações de download/abertura externa. MOV não é bloqueado por extensão ou tamanho comprimido; a reprodução original continua sob pressão moderada. A limpeza não apaga cache persistido, não gera nem publica outra prévia, não remove o original e não aumenta o teto global de 1 GB. Consumo e suporte do decoder ainda dependem do codec/resolução e do runtime instalado.

As URLs `https://media.organessonium.local/preview/<GUID>` são recursos internos interceptados por `WebResourceRequested`, não um servidor HTTPS real. Para vídeo, cada resposta fornece até 512 KiB disponíveis em RAM, com `206`, `Content-Range`, `Content-Length`, `Accept-Ranges` e `Cache-Control: no-store`. O Chromium solicita as faixas seguintes quando necessário. Isso evita que o WebView2 drene uma resposta integral antes de reproduzir. Há no máximo quatro respostas vivas por recurso; EOF/fechamento limpa e devolve o buffer a um pool limitado, sem alocar outro array grande a cada faixa. A leitura CDN cifrada também reutiliza buffers limitados à sessão do vídeo e os limpa após autenticar, inclusive em erro/cancelamento; somente o comprimento declarado do anexo entra na descriptografia. O cache plaintext e o teto global de memória não aumentam. Imagens, PDF e áudio preservam seus caches e usam o mesmo host virtual, sem listener localhost.

Uploads novos de MP4 elegível passam por `Mp4FastStart` antes da divisão/criptografia. O parser C# expõe uma sequência virtual que coloca `moov` antes do primeiro `mdat` e corrige `stco`/`co64`. Somente o índice `moov`, limitado a 32 MiB e admitido no orçamento global de RAM, é copiado em memória; áudio, vídeo e descritores são lidos por faixa do original. `PreparedVideoUpload.OpenRead()` deve ser usado para consumir essa sequência; `File` identifica a origem, não um arquivo remuxado. O original permanece intacto e não há cópia integral nem saída no TEMP. Estruturas não suportadas mantêm o upload original e registram erro. O FFmpeg é usado na geração de mídia auxiliar, não para alterar o conteúdo original. O checkpoint local `fastStartApplied` permite reconstruir os mesmos bytes ao retomar, sem misturar layouts de chunks; transferências antigas parcialmente enviadas preservam o layout anterior.

Miniaturas de imagens comuns (JPEG, PNG, BMP, GIF e TIFF dentro dos limites de dimensões e tamanho) usam WPF/WIC no processo, com decodificação limitada a 512 pixels no maior eixo, orientação EXIF preservada, duas gerações simultâneas e reserva de memória por geração. Não iniciam outra cópia gráfica do aplicativo. Imagens grandes, formatos não suportados e vídeos usam o FFmpeg embutido, separado e sem janela. O auxiliar Windows fica como fallback quando esse motor está indisponível ou não consegue decodificar a mídia; sua inicialização desativa explicitamente o cursor de feedback do Windows e conserva isolamento e limite do Job Object. Resultados são PNG para imagens e JPEG para vídeos, quadrados de 200×200, persistidos no cache cifrado e referenciados no metadata. O decoder reduzido reserva 64 MiB de trabalho, e o caminho isolado de miniatura reserva 96 MiB mais até 8 MiB de saída.

`MediaFileTypes` centraliza a classificação C# e os MIME de imagens/vídeos usados por entradas, upload, miniaturas e contagens dos seriais. Inclui HEIC/HEIF, AVIF, JXL, TIFF, JFIF, BMP/DIB, WebP, GIF, ICO/CUR, TGA e SVG, além de JPEG/PNG; vídeos incluem MOV/QT, MTS/M2TS, MPEG/VOB, WMV, FLV, OGV e 3G2, além dos formatos anteriores. A UI mantém a mesma classificação para cards, filtros e ícones das transferências, sem distinguir maiúsculas/minúsculas. Reconhecer o tipo não instala codecs nem garante reprodução nativa no WebView2; a geração de miniaturas depende do auxiliar Windows ou FFmpeg. O original é enviado sem conversão por essa classificação.

`FfmpegPreviewUpload` gera a prévia completa em uma única passagem do FFmpeg, antes de iniciar seu upload. Há uma fila de conversão 480p e outra de miniaturas FFmpeg, cada uma limitada a uma execução; uma conversão longa não retém a fila de miniaturas. Ambas continuam sujeitas à admissão global de memória. A espera e a conversão não ocupam uma vaga de envio de arquivo, e o controle do conversor é liberado antes de aguardar novamente uma vaga para transmitir. O resultado é gravado por I/O assíncrono em `.organessonium-preview-<GUID>/preview.mp4`, pasta com atributo Hidden na mesma localização do original. Upload de pastas e sincronização ignoram esse diretório interno. Não usa o TEMP do Windows, não copia o original e não grava ciphertext intermediário. O handle usa `DeleteOnClose` e permanece aberto durante o upload: sucesso, erro, cancelamento ou término do processo liberam o arquivo; a pasta vazia é removida no encerramento normal. Essa pasta pode ficar vazia após um encerramento abrupto. Hidden não é criptografia nem proteção contra leitura local: a prévia temporária está em claro. É necessário espaço e permissão de gravação ao lado do original; falhas preservam o original e são notificadas, sem fallback para outro disco. O tamanho final fornece o ChunkCount autenticado de ORGAESGC v1, eliminando a medição por segunda transcodificação.

A prévia é MP4 fragmentado (`empty_moov`, `frag_keyframe`, `default_base_moof`), H.264/YUV420p até 854×480 sem ampliar o original, 30 fps, vídeo alvo/máximo de 1.000 kbit/s e AAC estéreo de 96 kbit/s quando existe áudio. libx264 usa `veryfast`, `zerolatency` e até quatro threads; o filtro reduz a 30 fps antes da escala, evitando redimensionar frames que serão descartados; decodificação admite duas threads e `HardwareAcceleration` permite aceleração automática na decodificação. Duração e tempo codificado fornecem o progresso da geração. Não exige que duas codificações produzam bytes idênticos. A geração ainda depende de duração, resolução, codec, CPU/GPU e velocidade de leitura do original; não é instantânea nem há promessa de velocidade fixa.

A prévia usa o limite central de attachments, atualmente 20 MiB por parte cifrada, descontando os 70 bytes ORGAESGC do plaintext, e até dez anexos por mensagem. Depois de fechar a geração, o uploader existente lê suas faixas, cifra em RAM e usa descritores sob demanda, workers de transmissão, ACKs paralelos, retries e backpressure por bytes. Buffers são liberados ao terminar o corpo, sem esperar uma confirmação lenta. O gate global da biblioteca também controla a prévia e recebe mudanças do botão de 16 workers. Referências só são publicadas após confirmar todos os anexos. Prévias antigas de 2 MiB, MP4 flat, plaintext legado e transporte unitário permanecem legíveis; não há migração nem reenvio automático.

O FFmpeg reserva 192 MiB nativos, participa da admissão de buffers do backend e tem limite individual de 1 GB, separado do WebView2. Só sua saída convertida usa staging no disco; buffers criptográficos continuam limitados em RAM. Admissão aguarda até 30 segundos. Stderr não é salvo; são extraídos apenas duração/progresso, e logs de falha conservam tipo/HResult, sem nomes ou metadata. Windows de 32 bits ou instalações sem o componente conservam o transcoder Windows limitado a 128 MiB e aos codecs instalados. A licença e as fontes do componente estão em `media/NOTICE.md`.

O progresso fica no SQLite local, em `settings` sob `videoProgress:<fileId>`, com posição/duração em segundos, UTC da última reprodução e conclusão. O app grava a cada 10 segundos durante fluxo normal e força o último valor em pausa, fechamento, troca ou encerramento normal. Ao reabrir, restaura automaticamente a posição. A partir de 95% da duração, a próxima abertura começa no início; mudança de duração maior que o maior entre 5 segundos e 1% impede restaurar uma posição incompatível. Exclusão permanente remove o registro; registros sem atualização são limpos após 180 dias. Logout apaga o progresso junto aos dados da configuração anterior. Nada disso entra no metadata remoto.

O suporte de codecs permanece dependente do WebView2 instalado; não há transcodificação durante reprodução. Os contratos de reprodução acima não foram alterados pela cifra dos metadados.

## Lixeira

Na prova remota de referências, `storage-v2` é tratado como journal técnico, separado das pastas da biblioteca. Seus registros já passam pela leitura e validação do journal; a varredura de arquivos não baixa e decodifica novamente seus planos e recibos. As demais pastas continuam sendo consultadas remotamente antes de remover payloads.

Criar pasta, mover, enviar à Lixeira, restaurar e apagar definitivamente gravam primeiro a intenção no SQLite. O índice local combina o último serial confirmado com as alterações pendentes, refletidas imediatamente nos cards, sem esperar pela API. O worker retoma a fila dessa biblioteca ao reabrir o aplicativo. Em uma movimentação, os metadados de destino são preparados antes de enviar os seriais, pois o serial precisa do ID da mensagem que vai referenciar. O worker publica os seriais do lote e remove as mensagens antigas depois. Em uma exclusão definitiva, publica a remoção dos itens dos seriais antes de excluir os metadados. A limpeza física continua separada e silenciosa, com prova remota para proteger versões, leituras e referências compartilhadas.

Mover ou restaurar um lote mantém leases dos índices envolvidos e do journal durante a operação, inclusive nas leituras que atualizam seriais. A reserva de edição mantém o journal aberto até registrar sua conclusão; a recuperação de reservas locais também compartilha esse lease. A limpeza de payloads mantém os pools deste escritor abertos durante o lote. Assim, leituras auxiliares e escritas sucessivas não alternam arquivamento a cada registro, e o último lease encerra a escrita. Na criação de pasta pela interface, o card local aparece antes de qualquer gravação no Discord. A fila conserva a identidade da pasta e o título aleatório do post de índice. Ao reabrir, a rotina recupera o post pelo título e valida seu cabeçalho antes de continuar com o mapping, os metadados e os seriais. Para evitar a leitura de todas as páginas do pai, um serial válido com detalhes completos em cache delimita a busca por metadados novos. Um cache frio ainda usa a leitura completa para preservar as entradas e os totais do pai. É possível navegar e criar subpastas durante a espera. Uploads e gravações Markdown dentro da pasta aguardam sua confirmação.

A Lixeira é uma pasta técnica independente, com `folderId = trash`, caminho `/@trash`, post de índice no fórum `folders`, mapping em `names` e serial OSER v3 do tipo Folder no canal `serial`. Seu índice é criado na primeira abertura ou exclusão comum; ela não aparece como uma pasta da raiz. O anexo `.bin` e seu cache persistente seguem o mesmo fluxo das pastas normais, mantendo o ID da mensagem quando o conteúdo muda e preservando um serial vazio quando não há itens.

`Delete` e a ação comum de exclusão enviam os itens para a Lixeira após confirmação. `Shift+Delete` confirma a exclusão permanente e remove os payloads. O envio recuperável lê o metadata completo, publica no destino antes de remover a mensagem da origem e preserva identidade, chunks, criptografia, previews e favorito. O metadata do item recebe `parentFolderId: trash` e `trash: { originalParentFolderId, deletedAt }`, com data UTC. Pastas levam seus descendentes sem excluir os índices internos; apenas o pai da pasta movida muda. Pastas apagadas com nomes iguais permanecem separadas na Lixeira.

A barra lateral abre essa árvore isolada de Arquivos, Favoritos, Dispositivos e busca normal. O menu de um item oferece Restaurar. A barra de seleção restaura os itens marcados. Na raiz da Lixeira, Restaurar tudo age sobre o conteúdo completo, incluindo pastas com seus descendentes. O menu e a barra de seleção mantêm a exclusão permanente. `Delete` dentro dela não implica uma exclusão definitiva. Restaurar usa o pai original se ainda estiver ativo, ou `root` se ele não existir ou também estiver na Lixeira. Uma pasta com nome conflitante no destino bloqueia a restauração sem alterar o item. Na raiz dessa aba, `Esvaziar lixeira` pede confirmação e apaga permanentemente todo o conteúdo atual, incluindo descendentes e versões, independente de filtro ou seleção. O botão fica desativado durante a ação; falhas preservam os itens não excluídos. Não há limpeza automática nem expiração. `AppController.LibraryMutations.cs` mantém a fila e publica as mudanças locais. `AppRegistry.LibraryMutations.cs` prepara os metadados e seriais, guardando os dados completos do payload para retomar a operação. `AppRegistry.Trash.cs` fornece o acesso ao índice, a leitura dos itens e a resolução de destinos.

A seção Lixeira concentra o comportamento e os contratos dessa funcionalidade.

A exclusão permanente em lote usa quatro workers para ler os detalhes, registrar o intent durável e remover os metadados de cada arquivo. Os índices e o journal permanecem abertos durante essa fase, sem alternar arquivamento por item. Pastas são removidas depois dos descendentes. A remoção dos cards ocorre assim que a ação é gravada localmente. Em segundo plano, a limpeza faz uma única conferência remota das referências para o lote, consultando até quatro índices simultaneamente. Essa prova existe somente durante a operação, sob o gate do owner; não é um cache persistente nem substitui os checks de versões, referências compartilhadas, leituras ativas e downloads pausados. A edição dos attachments compartilhados continua serializada e revalidada para preservar outros arquivos da mesma mensagem. A limpeza não cria operações, notificações nem barras de progresso na interface. Uma conferência interrompida ou recusada conserva o intent e é retomada pelo ciclo de manutenção existente, além das ações de armazenamento. O diagnóstico registra a duração da prova e o resultado de cada item, sem nomes ou identificadores de arquivos.

Cada intent cifrado é confirmado no journal remoto antes da exclusão do metadata. Fechar ou encerrar o app não descarta essa pendência: na próxima abertura da mesma conta, a reconciliação recupera os intents não concluídos e retoma a conferência silenciosamente. Uma falha conserva os payloads e mantém o intent pendente. Uploads e alterações interativas interrompem a varredura e têm prioridade; a limpeza retoma quando terminam ou quando uma leitura protegida é liberada. O worker observa o encerramento da sessão e não reinicia em outra conta. A limpeza física não recarrega os cards da pasta em que o usuário está navegando.

## Persistência local

A migração de credenciais usa a exclusão segura do SQLite ao remover registros antigos.
Se o DPAPI não conseguir abrir um valor protegido, salvar preferências mantém esse valor
no banco para permitir recuperação ou substituição explícita.

O `README.md` é a documentação técnica geral do projeto. Documentos avulsos de desenvolvimento de features não integram o código-fonte distribuído; licenças, avisos legais e receitas de reconstrução das dependências continuam incluídos.

`EncryptedPreviewCache` grava miniaturas e prévias completas em blocos de 64 KiB autenticados com AES-256-GCM. Cada arquivo tem chave aleatória protegida por DPAPI para o usuário Windows atual, nonces distintos por bloco e cabeçalho autenticado. Plaintext só é entregue em RAM durante a leitura, inclusive em faixas de PDF/áudio; o arquivo cifrado é publicado por renomeação atômica. O cache não é portátil entre usuários Windows e não altera a criptografia ou os metadados no Discord. Caches anteriores em claro são removidos, não tratados como válidos. Downloads de prévia ainda usam staging operacional temporário fora de `Previews`, removido após uso; abrir em aplicativo externo ou inspecionar formatos que exigem caminho de arquivo também usa uma cópia temporária descartável, nunca o cache persistente cifrado como se fosse o original.

Na abertura, `App` e `MainWindow` compartilham a mesma inicialização de `SettingsStore`, evitando abrir e migrar o banco duas vezes. A sessão valida token e tipos dos quatro canais em paralelo; a conexão de presença do bot continua em segundo plano, sem bloquear a biblioteca, e é cancelada ao encerrar a sessão. A manutenção dos posts antigos começa depois de publicar os primeiros cards. A primeira renderização usa os totais locais enquanto reconcilia o servidor. Latência do Discord e inicialização do WebView2 ainda influenciam o tempo até a biblioteca.

A configuração inicial usa três etapas: Token, Segurança e Conexão. A primeira recebe o token e conserva as opções avançadas de nomes/IDs dos canais; `Avançar` apenas abre Segurança. Nessa segunda etapa, o usuário escolhe o modo de proteção e pode importar ou criar a chave antes de `Conectar`. O teste mantém a descoberta/validação dos canais e o fluxo de sessão existentes no C#. Uma conexão válida abre a biblioteca. Uma falha mostra uma tela com mensagem breve, `Configurar proxy`, `Tentar novamente` e `Revisar configuração`; valores de token, canais, proxy e segurança são conservados entre as etapas e tentativas. Canais ausentes ainda permitem criação automática. A interface bloqueia tentativas simultâneas e Enter não dispara conexões duplicadas. O campo de token mantém o botão de revelar/ocultar visível, sem sobrepor o texto. Quando já existe um token salvo, o campo pode ficar vazio e a conexão reutiliza a credencial armazenada. A senha de proxy salva nunca é preenchida na interface: o campo mostra apenas que existe uma senha e, se ficar intocado, o valor persistido é preservado. A rolagem fica abaixo da barra nativa. Proxy conserva seletores temáticos e movimento reduzido.

As configurações e os índices locais ficam em `organessonium.db`, dentro da pasta de dados. A tabela `settings` usa `key`, `value` e `updated_at`; cada gravação atualiza o valor e o horário em UTC pelo SQLite. O token do bot e a senha do proxy são gravados como valores protegidos pelo DPAPI no escopo do usuário Windows atual, com migração automática de registros antigos em texto simples. A interface recebe apenas indicadores de presença, nunca os valores. O logout remove esses registros junto com as demais configurações. `folder_index_map` persiste `folderId`, `threadId`, ID da mensagem em `names` e a referência do serial. `app_entries` é cache dos filhos já conhecidos, agrupado por `parent_folder_id`, e mantém também favorito, tipo de dispositivo, versão, modo e salt de criptografia sem armazenar qualquer chave.

O importador de `config.ini` preserva as preferências e remove o token correspondente quando confirma sua gravação no SQLite protegido por DPAPI. Uma credencial alternativa que ainda não foi importada é protegida no INI. O logout remove as credenciais dos INIs reconhecidos, inclusive fora da pasta de dados atual, antes de limpar o banco. A substituição é atômica. Se o arquivo estiver bloqueado, a migração pode concluir a gravação no banco e retomar a limpeza na próxima abertura. A migração não apaga backups ou cópias antigas.

Configurações > Downloads exibe a pasta Downloads resolvida pelo Windows como destino padrão, inclusive quando redirecionada para outro volume. Uma preferência vazia usa esse destino sem abrir um seletor a cada download; escolher outra pasta continua disponível e a escolha é persistida. Não há pasta temporária configurável. Os caminhos operacionais dos checkpoints legados continuam legíveis para permitir retomada/migração, sem recriar essa preferência na interface.

As tabelas `sync_folders`, `sync_state` e `sync_issues` guardam, respectivamente, vínculos por conjunto de canais, a última revisão aceita por caminho relativo e decisões pendentes. O cache `app_entries` conserva as extensões opcionais `sync` e `syncDevice`. O identificador da instalação fica separado em `%LOCALAPPDATA%\Organessonium\installation-id.txt`, sem token ou caminho das pastas, e não é apagado ao sair do bot. `SyncStaging` contém snapshots de upload em `OrganessoniumData`. Downloads novos da sincronização mantêm um arquivo técnico `.organessonium-sync-download-<hash>.content` e seu `.part` diretamente na pasta sincronizada, excluídos pelo scanner; a entrega à etapa de substituição usa renomeação, sem cópia integral. `SyncDownloads` pode conservar dados de checkpoints antigos, importados pela compatibilidade de download.

Ao abrir uma pasta, o cache é mostrado primeiro e a atualização usa o serial daquela pasta, com leitura de metadados como fallback quando o serial está ausente. A fase de cache consulta somente SQLite e seriais locais. Durante um lote de upload aberto, usa as entradas confirmadas do SQLite, que podem ser mais recentes que o serial; assim, uma pasta recém-criada não desaparece ao trocar de aba. A leitura remota do serial também preserva essas entradas até a publicação final do lote. A abertura mantém prioridade interativa sobre a manutenção silenciosa, que continua responsável pela reconciliação das mensagens. O thread é a fonte de associação dos filhos diretos; `parentFolderId` ausente em metadata legado é normalizado para a pasta que está sendo lida. O botão Atualizar e `F5` leem os mappings em `names` e os seriais da árvore, sem varrer mensagens de arquivos nem refazer seriais. Favoritos e Dispositivos também recebem somente os resultados dos seriais. O cache conhecido de uma pasta sem serial válido é mantido até a reconciliação silenciosa ou a reconstrução explícita. Os seriais locais não são apagados nessa operação. `Ctrl+F5` atualiza o mapping, limpa somente os seriais locais e os recria dos metadados do servidor. A publicação remota ocorre antes da troca de referência no mapping, sem exclusão em massa do canal. A contagem total de arquivos percorre recursivamente os seriais da árvore; os cards de pastas não exibem contagem. Uma leitura vazia dos mappings não substitui o mapa local existente. Uma atualização aplica inclusões, alterações e remoções somente aos mappings que continuam iguais ao snapshot local capturado antes da leitura remota. Referências e SHA-256 publicados durante essa leitura são preservados em memória e no SQLite; a confirmação local e a persistência do mapa usam o mesmo controle, sem manter esse controle durante a rede. Falhas temporárias, serial corrompido, thread inacessível ou HTTP 429 não removem o cache local válido: a operação é registrada e a interface continua com o último estado conhecido. Se o mapping de uma pasta foi perdido, mas o metadata ainda guarda o `threadId` do seu índice, a exclusão lê esse thread diretamente para remover os descendentes e a própria pasta. Em uploads e exclusões permanentes em lote, os metadados e caches são atualizados por item, mas cada serial afetado é publicado somente ao fim da ação. A exclusão permanente de uma pasta também remove seu mapping, serial e thread de índice depois de remover seus descendentes. A exclusão comum envia o item para a Lixeira, preservando payloads e índices descendentes.

O comando `--audit-metadata` faz uma leitura do canal `names`, dos threads do fórum `folders` e do canal `serial`, sem alterar o servidor, e grava `metadata-server-audit.txt` no diretório de dados. O relatório lista os metadados reconhecidos e aponta mensagens ilegíveis, seriais inválidos e referências sem metadata. O comando `--repair-serials` exige uma auditoria inicial sem metadados ilegíveis ou referências ausentes, refaz o cache local e publica os seriais a partir dos metadados, depois repete a auditoria. O relatório contém nomes e IDs privados da biblioteca e não deve ser publicado.

Ao confirmar `Sair`, o splash WPF da inicialização cobre Configurações durante a limpeza, sem mostrar a biblioteca anterior. O app encerra a sessão, cancela transferências e prévias em andamento, apaga configurações e entradas em cache do SQLite e limpa o diretório `OrganessoniumData`. Banco, caches, seriais e estados de transferência são removidos; o perfil WebView2 tem os dados de navegação, armazenamento e cache apagados pela API do runtime. Arquivos operacionais do runtime, logs técnicos e o UUID de escritor vinculado à instalação ficam preservados. Esse UUID não contém token nem dados dos arquivos e permite recuperar reservas interrompidas desta instalação ao reconectar. Se algum dado local não puder ser apagado, o splash sai e Configurações volta com a opção de tentar novamente. Prévias são canceladas e drenadas antes de apagar o cache, impedindo escritas atrasadas da sessão encerrada. Quando existe pasta operacional personalizada, o diretório padrão de AppData também é limpo para retirar resíduos de contas antigas. O cache de ferramentas FFmpeg, sem mídia do usuário, é preservado. Após a limpeza, a configuração inicial aparece sem token nem IDs dos canais anteriores; o banco é recriado apenas com a identidade operacional, sem exigir reinicialização do app.

## Interface desktop

Fechar a janela enquanto existem uploads ou downloads em andamento, aguardando ou pausados abre uma confirmação na interface. Cancelar mantém janela e transferências; confirmar respeita a configuração de fechar para a bandeja ou encerrar. No comando Sair da bandeja, a confirmação acontece antes de marcar o aplicativo como encerrando e parar os serviços. A mensagem informa se as transferências continuarão em segundo plano ou serão interrompidas.

Miniaturas são fornecidas como PNG/JPEG binário pelo host virtual `https://media.organessonium.local/thumbnail/`, interceptado pelo mesmo adapter das prévias, sem servidor ou porta local. O bridge envia somente URLs curtas, sem Base64 nem imagem embutida em código JavaScript. O cache de disco continua cifrado e é lido por blocos autenticados, com respostas `no-store`; a revisão da URL muda quando o conteúdo é salvo novamente. O cache C# mantém até 128 URLs, sem copiar o conteúdo das imagens para strings. A leitura dos detalhes de um arquivo consulta seu registro por `metadataMessageId`, usando o índice primário do SQLite, e atualiza somente esse registro, sem materializar ou regravar os outros arquivos da pasta. A navegação e a publicação de cards não forçam coletas do heap. O limite de 1 GB vale para cada processo do backend, sem somar o navegador.

A biblioteca admite inicialmente até 100 itens, contando pastas e arquivos, e acrescenta mais 100 ao descer perto do fim. Os cards anteriores e as miniaturas já carregadas permanecem na grade até a troca de pasta ou uma remoção efetiva. Busca, ordenação, seleção de todos, previews e operações consideram a coleção completa. Trocar pasta, filtros ou ordenação reinicia a página; alternar grade/lista conserva a quantidade admitida. A lista mantém linhas dos itens admitidos, sem decodificar miniaturas. Alterações em outra pasta preservam os elementos, as imagens, a seleção e a posição de rolagem da pasta aberta.

A janela principal usa a WebView2 dentro de uma shell WPF. O primeiro frame exibe um splash WPF leve, com o ômega centralizado e pulsação suave, antes de abrir o SQLite e inicializar a WebView2; esse trabalho persistente começa somente depois que a janela já foi renderizada. No Windows 11, o `AppWindowTitleBar` do Windows App SDK estende a shell para a faixa superior, mas o sistema continua desenhando e operando minimizar, maximizar/restaurar e fechar. A WebView recebe os insets reais dos botões para não colocar ações sob eles, e as regiões vazias da barra e da marca lateral são marcadas como arrastáveis. Essas regiões são reaplicadas após alterações de layout; ao abrir uma prévia, a região acompanha o cabeçalho visível e exclui seus controles clicáveis. Configurações conserva a barra superior e suas regiões de arraste. Em Windows sem suporte ou se a inicialização falhar, o app preserva a moldura WPF padrão. A barra lateral tem a marca do Organessônium e um botão de painel para recolher sua largura. Recolhida, ela mostra o ômega e revela o botão de expansão ao passar o mouse sobre a marca, ocultando a marca sob o botão durante a transição. Os ícones dos comandos laterais usam slots fixos nos dois estados, então permanecem ancorados enquanto a largura anima; os rótulos aguardam o fim da expansão e entram ou saem por opacidade, sem quebra de linha. O botão destacado `Novo` abre as opções `Pasta`, `Arquivo de texto (.md)`, `Upload de arquivos` e `Upload de pastas`; ele permanece no mesmo lugar, mas fica desativado em Favoritos, Dispositivos e Lixeira para não deslocar a navegação. As mesmas ações de arquivos continuam disponíveis no menu de contexto da área de arquivos. A área de arquivos exibe o caminho da pasta na mesma linha do nome atual e, logo abaixo, filtros de tipo e data, ordenação, visualização e atualização do índice. A seleção por arraste começa e permanece somente na região dos cards, abaixo do cabeçalho. A barra lateral mantém o acesso a Arquivos, Favoritos, Dispositivos sincronizados, Lixeira e Configurações; as transferências continuam visíveis no painel próprio de operações. O menu de cada arquivo ou pasta permite adicionar e remover o item dos favoritos, e a alteração aparece imediatamente tanto na grade atual quanto na aba Favoritos. A aba Dispositivos mostra as raízes publicadas sob `synchronized` e permite navegar progressivamente pela árvore compartilhada. Não há área de compartilhamento nem perfil de usuário.

A ponte WebView2 aceita mensagens somente do documento local `index.html` ou `setup.html` de nível superior, com comandos em allowlist, limite de tamanho, profundidade controlada e estrutura validada. Frames e qualquer outra origem são rejeitados antes de alcançar o controlador. Navegação externa, novas janelas, downloads e permissões do navegador são bloqueados no WebView2 privilegiado; links `http`, `https` e `mailto` legítimos são abertos no aplicativo padrão fora da WebView2. O conteúdo Markdown só aceita esses mesmos esquemas em links e `http`/`https` ou os hosts internos de imagem em imagens, com remoção de scripts, eventos e estilos não permitidos. As páginas locais usam CSP restritiva e não carregam scripts ou conexões externas.

A barra lateral e a barra superior usam o fundo contínuo da janela. A grade e a lista de arquivos ficam em uma única área de cards levemente mais escura, com cantos arredondados. Na grade, o tamanho Médio apresenta seis cards por linha em 1920×1080 com a barra lateral aberta; a quantidade de colunas aumenta ou diminui com a largura disponível. O card inteiro é quadrado, incluindo o cabeçalho de 44 px: a miniatura é mais baixa que larga, com margem interna de 8 px, e não aumenta a altura do card. Os cards têm cantos de 12 px e espaçamento de 16 px; o tamanho Médio usa base de 240 px e limita a expansão individual a 300 px. Pequeno e Grande preservam a mesma proporção, e os chips de pasta continuam com 48 px de altura. Os thumbnails visíveis e uma linha adicional abaixo da tela são solicitados na ordem dos cards, carregados com concorrência limitada pela configuração `Prévias simultâneas` e entregues à interface de cima para baixo. A margem inferior acompanha a altura real dos cards, o espaçamento e o deslocamento da imagem após o cabeçalho, ajustando-se à largura e ao tamanho da grade. As imagens já carregadas permanecem nos cards fora da tela; o cache auxiliar JavaScript conserva até 128 URLs, sem descarregar essas imagens. O rodapé de status anterior não é exibido; mensagens continuam acessíveis pela região `aria-live`, enquanto atividades em segundo plano e transferências usam painéis separados. O resumo lateral fica no rodapé, separa o armazenamento por uma linha e mostra bytes e a quantidade total em formato compacto, como `8,43 GB 312 itens`, usando imediatamente o último agregado completo dos seriais, salvo no SQLite, ou o agregado dos seriais locais quando ainda não há snapshot. A leitura remota atualiza esse valor sem zerá-lo durante a espera: `AppRegistry.GetLibraryStatisticsAsync` soma os agregados diretos de cada pasta da árvore, e `AppController` entrega o resultado à WebView2. Uma biblioteca vazia é mostrada como `0 B` e `0 itens`. Um ícone animado junto desse resumo permanece visível enquanto alguma leitura ou reconciliação com o servidor está em andamento, inclusive com operações sobrepostas, e desaparece somente depois que todas terminam. Assim, o resumo não trata apenas os filhos da pasta atualmente aberta como a biblioteca inteira. Configurações ocupa a área de conteúdo como uma seção da navegação, conservando a barra lateral e a barra superior. Voltar na barra superior ou pressionar Escape retorna à pasta ou à guia do editor que estava aberta, sem recriar seu conteúdo. O editor Markdown abre em suas guias locais; sua barra de formatação acompanha a largura útil da área de trabalho e mantém os ícones visíveis no modo compacto.

O editor Markdown mostra o estado do salvamento na guia. O conteúdo continua passando pelo versionamento normal sem aparecer no painel de uploads. Ao fechar uma guia com alterações, ela aguarda a confirmação do conteúdo mais recente. O documento preserva as referências originais de imagem no texto. O editor resolve imagens do Drive pela identidade do arquivo e anexos cifrados pela mensagem na thread atual ou nas threads das versões do documento. As imagens são servidas pelo host virtual da WebView2 enquanto a guia está aberta. A ferramenta Tabela permite escolher de 1 a 20 linhas (contando o cabeçalho) e colunas nos dois modos. A conversão preserva alinhamento, células vazias e barras verticais escapadas.

A reconciliação de metadados em segundo plano mantém a coleção do backend atualizada por pasta. O bridge publica somente os itens da pasta conferida, em vez de reenviar toda a biblioteca a cada resultado. Na WebView, arquivos de outras pastas são incorporados sem renderizar novamente a pasta visível. Atualizações da pasta atual recebidas enquanto Configurações ou o editor estão abertos são aplicadas à área de arquivos ao retornar, preservando a coleção completa para busca e navegação.

As configurações têm categorias exclusivas: Aparência, Desempenho, Miniaturas, Uploads, Downloads, Proteção, Conexão e Aplicativo. Somente a categoria selecionada aparece, com cards, controles e cores derivados da paleta existente. As opções de proxy e conta ficam em Conexão; inicialização, armazenamento local e diagnóstico ficam em Aplicativo. Os ajustes mantêm o salvamento automático, inclusive ao sair da página. As categorias aceitam as setas, Home e End. A transição ocorre ao mudar de categoria e clicar na ativa conserva a página e a rolagem. O layout passa a uma coluna em janelas menores. Enquanto Configurações está aberta, atalhos de exclusão, renomeação e atualização da biblioteca não atuam sobre arquivos ocultos.

Os combos das configurações conservam os selects e seus eventos de alteração como contrato de dados, com um botão e uma lista de opções estilizados pela paleta do app. A lista mostra a seleção com marca de confirmação, aceita teclado e fecha ao escolher, pressionar Escape, clicar fora, trocar categoria ou sair da página. Ela é posicionada sobre o conteúdo e limitada à janela, sem ser cortada pela rolagem dos cards. O idioma mantém seu seletor existente. O nome da categoria e dos controles de miniaturas corresponde aos thumbnails; o ícone dessa categoria é neutro. Prévias de vídeo 480p continuam identificadas como prévias de vídeo.

A categoria Proteção mostra sempre o modo confirmado em uso, com um indicador de estado destacado. A criptografia dos novos uploads permanece ativada nos modos Padrão e Chave personalizada; a escolha altera a origem da chave. Abrir a configuração da chave personalizada não a ativa: o cabeçalho e a etiqueta `Em uso` continuam refletindo o modo confirmado até a ativação. A disponibilidade de uma chave salva aparece separadamente. Quando a chave já está disponível, a página oculta o campo de senha e reutiliza a chave armazenada, sem derivar outra. A ativação exige confirmação em diálogo, tanto para criar uma chave quanto para usar a chave salva; cancelar mantém o modo anterior. Não há checkbox de confirmação nessa página. A exportação exige uma senha de recuperação com pelo menos 8 caracteres e grava um envelope autenticado `OEK2`; a importação pede essa senha e ainda aceita arquivos `OEK1` antigos, avisando que eles não têm proteção por senha. Importação e exportação preservam suas confirmações. Botões de proteção e tema têm seletores independentes.

Todos os ícones de ações, menus e tipos de arquivos da WebView2 usam a fonte local Google Material Symbols Rounded, inclusive na configuração inicial e no editor, sem dependência de rede. Ações e tipos comuns são cinza `#c4c7c5` no tema escuro e `#5f6368` no claro. Imagens e vídeos usam vermelho `#ea4335`; estrelas de favoritos usam amarelo `#fbbc04`. Pastas usam o glyph preenchido e mantêm as cores de pasta configuradas pelo usuário. Na navegação lateral, Arquivos usa âmbar, Favoritos amarelo, Dispositivos azul e Lixeira vermelho suave; no modo claro esses quatro tons usam respectivamente `#c77800`, `#c58b00`, `#0078bd` e `#cf3f45` para maior saturação/contraste. A engrenagem de Configurações permanece cinza nos dois temas, independente da cor de destaque. O ômega e o ícone de marca do aplicativo continuam sendo identidade visual, não ações. Abrir/pré-visualizar continua disponível por duplo clique, mas não aparece no menu dos três pontos.

A fonte `web/fonts/MaterialSymbolsRounded.woff2` inclui o eixo variável `FILL` de 0 a 1, com tamanho óptico 24 e peso 400. Isso permite preencher pastas/estrelas/mídia e manter as demais ações contornadas no mesmo recurso local. Uma fonte estática contornada ignora esse eixo mesmo quando o CSS declara `FILL: 1`. A licença Apache 2.0 acompanha o recurso em `web/fonts/LICENSE`; consulte o [guia oficial de Material Symbols](https://developers.google.com/fonts/docs/material_symbols) para o contrato dos eixos.

`Aparência > Cor de destaque` permite seguir a cor do Windows (padrão), escolher uma paleta de cores do Windows ou informar uma cor personalizada pelo seletor/hexadecimal. `WindowsAccentService` lê `UISettings.GetColorValue(UIColorType.Accent)`; `MainWindow` acompanha `ColorValuesChanged` e encaminha mudanças pelo bridge, sem modificar as preferências do Windows. `accentColorMode` (`system`, `preset`, `custom`) e `accentColor` (`#RRGGBB`) são persistidos na tabela `settings` e preservados no clone da configuração. `web/appearance.js` aplica os tokens CSS, ajusta tons extremos para contraste de pelo menos 3:1 nos controles e seleciona texto claro/escuro para botões preenchidos. Uma escolha explícita de paleta ou cor personalizada não é substituída por mudanças no Windows. Referência da API: [GetColorValue](https://learn.microsoft.com/en-us/uwp/api/windows.ui.viewmanagement.uisettings.getcolorvalue?view=winrt-26100) e [ColorValuesChanged](https://learn.microsoft.com/en-us/uwp/api/windows.ui.viewmanagement.uisettings.colorvalueschanged?view=winrt-26100).

O botão lateral selecionado mantém texto e preenchimento cinza, com uma linha compartilhada na cor de destaque que se desloca entre os botões, incluindo Configurações. Contorno/preenchimento dos cards selecionados, seleção na lista e retângulo de seleção por arraste usam tons neutros nos dois temas, sem acompanhar a cor de destaque. Os estados ativos dos botões de visualização, tema, tamanho dos cards e formatação também são neutros. Trocas entre Arquivos, Favoritos, Dispositivos, Lixeira e guias do editor usam entrada de conteúdo por opacidade e deslocamento vertical de 14 px durante 220 ms, sem animar ou reiniciar as coleções/requisições. Na biblioteca, a animação atua no cabeçalho e nas listas internas; `main-area`, seu fundo escuro, margens e cantos permanecem fixos. A seleção por arraste atualiza o retângulo e os cards no máximo uma vez por frame. A identificação de itens da Lixeira usa um mapa de parentes por pasta, evitando varrer toda a coleção para descobrir o pai de cada arquivo a cada movimento do mouse. O indicador de upload por arrastar e soltar aceita somente formatos nativos de arquivos; textos e seleções da interface não o ativam. A entrada e a saída do indicador usam opacidade, com deslocamento e escala suaves no conteúdo. O menu de contexto entra com opacidade, deslocamento de 4 px e escala de 98% a 100% durante 140 ms. Uma atualização assíncrona dos dados do menu não reinicia a entrada. As transições respeitam `Animações` desativadas. A cor de destaque continua disponível na linha lateral, controles e indicadores de progresso, independente da escolha entre tema claro, escuro e do sistema.

## Versões, cópia e informações de arquivos

O menu de arquivos inclui `Fazer cópia`, `Ver informações` e, quando o metadata completo contém histórico, `Versões`. Os textos são `Adicionar à pasta "Com estrela"`, `Fazer o download`, `Renomear`, `Mover` e `Mover para a lixeira`. Remover o favorito usa `Remover da pasta "Com estrela"`. Não foram adicionadas ações de compartilhamento ou disponibilidade off-line. A restauração/exclusão permanente da Lixeira e os controles de cor das pastas já existentes continuam disponíveis.

Escolher `Substituir` envia novo lote/salt preservando fileId e o conteúdo anterior. Novo conteúdo de até 1 GiB usa pool do escritor; maior usa dedicado, reaproveitando o dedicado atual quando aplicável. A versão pode mudar de thread/layout, mas os snapshots históricos não são movidos. `versions: [{ versionId, archivedAt, payload }]` conserva os metadados completos de cada conteúdo, sem histórico aninhado. A publicação revalida a versão/batch remoto sob claim e só altera metadata após confirmação das partes/prévias; conflito não sobrescreve outra versão silenciosamente. Histórico continua cifrado sem alterar OSER/envelope. Markdown usa o mesmo pipeline de upload/versionamento.

`uploadedAt` conserva o upload inicial; `versionUploadedAt` registra o conteúdo atual e `modifiedAt` acompanha substituição, rename, move e edição. Metadados antigos sem essas datas adicionais usam a data de upload como fallback. `AppController.Files` e `FileVersioning` cuidam da publicação e das ações, enquanto `MetadataService` valida e cifra o JSON. O SQLite persiste as versões e datas em colunas aditivas; materializar seriais preserva detalhes compatíveis e descarta referências antigas quando o salt/thread/thumbnail indicar outro payload. As operações que alteram a organização preservam os detalhes completos, não apenas os cards do serial.

O diálogo de informações de arquivos mostra categoria/MIME, localização (`/`, `/Fotos` etc.), tamanho atual, tamanho utilizado, upload inicial, última modificação, `threadId`, ID da mensagem de metadata e número lógico de chunks. Para pastas, o título e os rótulos se adaptam: a última linha mostra quantidade de arquivos, o tamanho da pasta soma os conteúdos atuais e o tamanho utilizado inclui as versões retidas de todos os arquivos descendentes. `AppRegistry.FolderInformation` percorre as subpastas com proteção contra ciclos e duplicação de identidades. Seriais e detalhes locais completos são reutilizados; um índice sem os tamanhos/históricos necessários é hidratado pelos metadados antes de apresentar os totais. Pastas vazias apresentam zero. Tamanho do arquivo mostra o `sizeBytes` do conteúdo atual. Tamanho utilizado e o resumo lateral somam os originais atuais e retidos, acrescentando `preview.video480p.sizeBytes` a cada versão que tem prévia. Miniaturas, overhead criptográfico e uploads órfãos ficam fora da soma. Seriais antigos recebem o total corrigido na reconciliação normal da pasta ou ao atualizar o índice; não há alteração do formato OSER. O histórico mostra o conteúdo atual e os anteriores, com download de cada versão. Downloads guardam um snapshot do metadata no checkpoint para não trocar o conteúdo após uma substituição durante a retomada.

O diálogo de informações abre imediatamente com os nove campos na estrutura final, cada valor mostrando `Carregando...` até a leitura terminar. Um texto `Carregando informações...` e um indicador giratório neutro acompanham a espera; o espaço desse status é reservado para evitar mudança de altura quando os valores chegam. A resposta substitui os valores e encerra o indicador, sem abrir outro diálogo. Erro ou fechamento também encerram o indicador, e respostas antigas não atualizam outro item aberto. O estado de espera expõe `aria-busy` e respeita animações desativadas.

`Fazer cópia` baixa o conteúdo atual autenticado para um diretório temporário operacional e o envia como arquivo independente na mesma pasta, com nome `Cópia de <nome>` e sufixo quando necessário. Recebe outro fileId, salt, metadata e attachments; pode usar o mesmo pool físico, sem copiar favorito/histórico nem reutilizar os attachments do original. A criptografia de upload permanece em RAM; o reconstruído temporário é removido ao final. A ação é para arquivos, não árvores de pastas.

A especificação para clientes interoperáveis está em [Versões e informações](#versões-cópia-e-informações-de-arquivos). A criptografia continua em [Payloads criptografados](#payloads-criptografados), o transporte em [Upload e transferências](#upload-e-transferências) e as compatibilidades transitórias em [Download, integridade e compatibilidade](#download-integridade-e-compatibilidade).

## Sincronização de pastas entre computadores

### Identidade, árvore e cadastro

Dispositivos preserva as galerias já publicadas e inclui computadores com `deviceType: "pc"`. O nome exibido vem de `Environment.MachineName`; a identidade é um `deviceId` persistente, não esse nome. Cada instalação tem uma raiz `pc-<deviceId>`, por isso computadores homônimos não são consolidados.

`Adicionar pasta sincronizada` usa o seletor nativo do Windows e permite nome, caminho local, automação, bidirecionalidade, políticas de conflito/exclusão e inicialização com Windows. O `syncFolderId` identifica a pasta lógica, independentemente do caminho físico. A raiz canônica usa `folderId = sync-<syncFolderId>`. Em outro computador, `Sincronizar esta pasta neste computador` associa o mesmo conteúdo a um novo caminho e cria uma entrada de navegação com `sync.canonicalFolderId`; não duplica os payloads. Subpastas mantêm caminhos relativos com `/` e índices hierárquicos separados. Remover o vínculo desativa somente a associação local, sem apagar arquivos locais ou remotos.

Pastas vazias no primeiro vínculo recebem o conteúdo remoto. Conteúdo local idêntico é reconhecido pelo hash; diferenças são tratadas como conflito antes de substituir qualquer arquivo. Pastas locais sobrepostas, a pasta de dados do app e raízes com reparse point são rejeitadas.

### Comparação, automação e transferências

O sincronizador compara estado-base persistido, estado local e revisões remotas. Datas UTC e tamanho evitam hashes desnecessários, mas a igualdade de conteúdo é confirmada por SHA-256 quando necessário. Eventos do watcher invalidam a assinatura daquele caminho mesmo quando tamanho e timestamp coincidem. O watcher aplica debounce de 2,5 segundos e reúne caminhos afetados; overflow solicita reconciliação completa. A consulta remota ocorre a cada minuto nas pastas automáticas e uma varredura local completa ocorre a cada cinco minutos. A primeira execução, a retomada, uma falha e `Sincronizar agora` também fazem varredura completa.

O worker executa fora da thread gráfica, com fila limitada e exclusão mútua por pasta. Arquivos são processados sequencialmente; seus chunks usam o paralelismo configurado e o limitador REST existente. Arquivos instáveis, bloqueados ou inacessíveis são adiados. Varreduras incompletas nunca autorizam exclusões. Falhas de conexão preservam estado e cópias, com espera progressiva de até cinco minutos antes de nova tentativa. Pausa global e pausa por pasta persistem; retomar reconcilia as mudanças. Encerrar o processo cancela o trabalho sem gravar uma nova preferência de pausa.

Uploads capturam uma cópia estável em disco, validam o hash e reutilizam `ForumUploader`, `TransferManager` e `EncryptionService`. Só depois de confirmar chunks e revisão, os metadados navegáveis, caches e seriais são atualizados. Uma confirmação `syncApplied` permite reparar publicação interrompida sem reenviar o arquivo. Downloads reutilizam `ForumDownloader` e os checkpoints; o arquivo anterior não é tocado até validar tamanho/hash e preparar a troca atômica no mesmo volume. Há uma cópia local de recuperação em `.organessonium-recovery` quando uma versão existente é substituída ou removida. Não há leitura integral de arquivos grandes para RAM.

As transferências do worker aparecem no painel quando a janela existe. Progresso e notificações não abrem a interface. As pastas mostram sincronização, pausa, espera por conexão ou decisões pendentes; os modais permitem resolver arquivos individualmente ou confirmar atualizações remotas em lote.

### Revisões, conflitos e exclusões

Os metadados comuns continuam em `schemaVersion: 2`. Arquivos sincronizados recebem `sync.version: 1`, `syncFolderId`, `relativePath`, SHA-256, `modifiedUtc`, revisão numérica, `revisionId`, dispositivo e estado. Raízes e aliases incluem apenas os campos aplicáveis. O OSER publicado continua v3; detalhes da sincronização são obtidos dos metadados, não de uma alteração do formato binário.

O índice da raiz canônica conserva um diário versionado de revisões com `parents` e referências ao payload já existente. A revisão numérica e o relógio não arbitram concorrência: duas revisões sem relação de ancestralidade são conflito. A publicação confirma a revisão remota antes de trocar o índice navegável. A limpeza retém as revisões atuais, suas bases imediatas e todos os ramos em conflito; não é um histórico ilimitado nem um serviço de backup.

Por padrão, uma alteração somente remota pede confirmação. `Substituir arquivo local` pode memorizar atualizações automáticas para aquela pasta; isso não autoriza resolver conflitos reais por timestamp. Alterações dos dois lados permitem manter a versão local, usar a nuvem ou manter ambas com nome contendo dispositivo e data. A decisão é revalidada antes de executar, para não aplicar uma escolha sobre conteúdo que mudou depois.

Exclusões usam `state: "deleted"`, `deletedUtc`, origem e uma nova revisão, não a ausência de um arquivo ou thread. As políticas são perguntar, propagar ou ignorar. Exclusão remota com edição local é conflito. Diretórios não vazios não são removidos recursivamente pelo worker. Renomeações locais com hash único reaproveitam `fileId` e chunks; renomeações remotas preservam a mesma identidade e respeitam a confirmação/configuração da pasta. Tombstones não são itens da aba Lixeira.

### Execução sem interface e inicialização

O evento `Closed` libera imediatamente a referência à janela principal. A liberação é idempotente e não altera uma janela substituta; abrir novamente cria outra instância em vez de chamar `Show()` em uma janela já fechada.

`App.xaml` não usa mais `StartupUri`. No modo normal, o primeiro frame continua sendo o splash WPF. O `App` mantém um `SyncBackgroundHost` independente do `AppController`. Fechar com `Minimizar para a área de notificação` oculta a mesma janela, sem descartar controller ou WebView2: uploads, downloads e sincronização continuam, e guias, pasta atual e posição de scroll permanecem no DOM. Abrir pelo ícone restaura essa janela, sem uma nova conexão ou recarga da biblioteca. Essa preservação vale para a sessão em execução, não como restauração de guias após encerrar o processo. O menu oferece abrir, sincronizar agora, pausar/retomar e sair; sair cancela workers, libera recursos e encerra o processo. Sem a opção de bandeja, o fechamento real conserva o fluxo de encerramento e os checkpoints para retomada.

`Organessonium.exe --background` não cria `MainWindow` nem inicializa WebView2. Um mutex e pipe limitados ao usuário impedem workers duplicados e permitem que uma segunda abertura solicite a janela à instância existente. Não existe executável adicional ou serviço Windows instalado.

A inicialização é opt-in em Configurações. MSI/execução sem pacote registram o executável atual, entre aspas e com `--background`, em `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. MSIX usa a extensão `windows.startupTask`, tarefa `OrganessoniumSync`, declarada desativada e habilitada por `StartupTask.RequestEnableAsync`; o manifesto inclui `uap10:Parameters="--background"`. O app não reativa uma tarefa bloqueada pelo Gerenciador de Tarefas. A preferência de fechar no tray é separada e não muda silenciosamente.

### Limites e validação

- Junctions, symlinks e reparse points não são sincronizados; caminhos absolutos, `..`, UNC, nomes inválidos e saídas da raiz são bloqueados. Temporários internos, `Thumbs.db`, `desktop.ini`, `~$*` e `*.tmp` são excluídos. `.git`, `bin`, `obj` e `node_modules` continuam incluídos.
- Não há merge de arquivos arbitrários, lock distribuído/CAS no Discord, regras personalizadas de exclusão nem recuperação automática de uma identidade de instalação perdida.
- O sincronizador exige revisões `syncRevision` para mudanças remotas. Edições por clientes/fluxos que alteram apenas os metadados comuns, incluindo ações normais da biblioteca, não são convertidas automaticamente em revisões. Para editar uma pasta sincronizada com propagação, use o caminho local vinculado. Navegação, previews e downloads continuam usando os objetos comuns.
- Vídeos sincronizados mantêm os bytes originais para preservar o hash; esse upload não aplica faststart nem gera preview 480p. Miniaturas dependem do suporte do Windows Shell. Chunks parciais de downloads abandonados e cópias `.organessonium-recovery` não têm expiração automática.
- Os testes sem interface validam duas instalações isoladas, conflitos, exclusões, falhas, caminhos, persistência e o protocolo remoto com HTTP simulado. Não substituem validação em dois computadores reais, Discord real, login do Windows, pacote MSIX instalado ou consumo durante horas. A interface não deve ser aberta para testar enquanto o usuário estiver usando o computador.

O diário e as confirmações de sincronização usam o mesmo codec antes de serem consumidos pelo worker. Payloads pequenos novos usam shared com chunkRefs/thumbnailRef/storage no snapshot; grandes e retomadas legadas mantêm seu layout. A limpeza de revisão persiste intent antes de retirar journal e usa GC seletivo, protegendo heads/bases/conflitos e referências externas. Transporte dedicado está em [Upload e transferências](#upload-e-transferências), shared em [Armazenamento compartilhado V2](#armazenamento-compartilhado-v2), criptografia em [Payloads criptografados](#payloads-criptografados) e fallbacks em [Download, integridade e compatibilidade](#download-integridade-e-compatibilidade). Não muda os bytes originais nem as regras de conflito/tombstone.

## Geração de releases para Windows

`dotnet publish` e `build-releases.bat` executam `media/Verify-Sources.ps1` antes da publicação. Releases públicas são bloqueadas enquanto as fontes não estiverem conferidas ou se houver divergência de SHA-256 entre o manifesto, o pacote embutido e as fontes correspondentes. O runtime nativo, suas DLLs e os avisos ficam em `media/runtime-package.zip`, embutido como recurso do assembly. `EmbeddedMediaRuntime` prepara esse pacote uma vez por sessão em `%LOCALAPPDATA%\Organessonium\Media\<sha256>`, por I/O em background, com lock entre processos, conferência dos arquivos existentes e renomeação de arquivos parciais validados. Não usa TEMP nem extrai conteúdo do usuário. Uma nova versão tem outro diretório de cache. O EXE portátil não exige pasta `media` externa. Instalações de desenvolvimento antigas sem o pacote ainda aceitam o motor externo. Licenças, inventário e procedimento de reconstrução estão em [media/NOTICE.md](Organessonium/Organessonium/media/NOTICE.md) e [media/build/README.md](Organessonium/Organessonium/media/build/README.md). A build controlada mantém os codecs anteriores, com fontes/receitas assinadas MSYS2, componentes adicionais fixados e crates Rust incluídos. O projeto de testes reutiliza a inicialização do Windows App SDK do assembly do app, sem gerar inicializadores duplicados.

`build-releases.bat` gera os artefatos em `artifacts/releases/<versão>-build.<n>` sem alterar o pacote portátil existente. A versão vem exclusivamente de `Version.props`; se um valor for informado no comando, por exemplo `build-releases.bat 1.2.0`, ele apenas confirma a versão pública atual e nunca a substitui. Use `-SkipStorePackages` para gerar apenas portáteis, MSIs, fontes e metadados, sem MSIX nem MSIXBundle; nesse modo o WACK não é aplicável. Os três MSIX e o MSIXBundle recebem `A.B.C.0`, enquanto o Windows Installer usa os três primeiros campos para controlar upgrades do MSI.

`Organessonium.exe --verify-media-runtime` confere/prepara o pacote e executa uma pequena operação de mídia em RAM, retornando 0 em sucesso ou 1 em falha. Esse modo não abre WPF/WebView2, não carrega configurações nem acessa o Discord. O gerador usa essa verificação no EXE publicado da arquitetura da máquina; pacotes de outras arquiteturas recebem conferência estrutural, não uma alegação de execução em outro dispositivo.

- `Organessonium-windows-source.zip` contém solução, C#/XAML/web, assets, documentação, ferramentas de construção do motor, licenças, pacote nativo embutido e `Organessonium/media/sources/ffmpeg-corresponding-source.zip`. Também inclui `Version.props`, `Directory.Build.props`, `global.json` e `NuGet.config`, permitindo compilar e conferir a versão em uma extração limpa. O arquivo completo de fontes FFmpeg também é entregue separadamente. Entradas usam `/`; `bin`, `obj`, caches, logs, bancos, certificados e configurações locais não entram. O gerador verifica dados locais/segredos antes de criar o ZIP. Não substitua este artefato pelo ZIP automático do GitHub, que não contém os inputs de mídia ignorados pelo Git.
- `Organessonium-installer-x86.msi`, `Organessonium-installer-x64.msi` e `Organessonium-installer-arm64.msi` são produzidos pelas APIs nativas do Microsoft Windows Installer e pelo `MakeCab` do Windows. O Windows Installer exige um pacote distinto por arquitetura, portanto não existe um único MSI misto. Cada instalador contém a publicação multi-file framework-dependent correspondente, em cabinet sem compressão, e instala somente para o usuário atual em `%APPDATA%\Organessonium`, ao lado de `%APPDATA%\OrganessoniumData`, sem exigir elevação. Os atalhos do Menu Iniciar e da Área de Trabalho também pertencem apenas ao usuário atual. O instalador impede downgrade, preserva o `UpgradeCode` x64 existente e usa códigos fixos próprios para x86 e ARM64.
- `msix/Organessonium_<versão>_x86.msix`, `msix/Organessonium_<versão>_x64.msix` e `msix/Organessonium_<versão>_arm64.msix` contêm, cada um, o executável self-contained e single-file da própria arquitetura.
- `Organessonium_<versão>.msixbundle` reúne exatamente os três MSIX. Cada pacote inclui os avisos e as fontes completas do motor em `media/sources/ffmpeg-corresponding-source.zip`, sem depender de URL externa para entregá-las ao usuário da Store. Isso aumenta seu tamanho. O `MakeAppx` recebe `/bv` explicitamente.
- `Organessonium-x86.exe`, `Organessonium-x64.exe` e `Organessonium-arm64.exe` são os portáteis self-contained, com motor e licenças embutidos. Publique o executável da arquitetura desejada junto do ZIP de código-fonte da mesma versão no GitHub.
- `build-info.json` registra versão, build, versão de pacote, tag, commit, estado da árvore, data UTC e identificação do workflow.
- `SHA256SUMS.txt` registra os hashes dos MSIs, EXEs portáteis, ZIP de código-fonte, fontes FFmpeg e `build-info.json`; com os pacotes da Store habilitados, também registra os MSIX e o MSIXBundle.

Para envio à Microsoft Store, use os valores de `storeIdentityName`, `storePublisher`, `storePublisherDisplayName` e `storeDisplayName` da reserva no Partner Center. O último campo define tanto `Package/Properties/DisplayName` quanto o nome visível do aplicativo no manifesto. Se for necessário usar valores diferentes dos padrões de `release/release-settings.json`, copie `release/release-settings.local.example.json` para `release/release-settings.local.json` e preencha os campos exatos. O arquivo local é ignorado pelo Git, não entra no ZIP e não deve ser publicado. O fluxo normal da Store não exige PFX: o bundle pode permanecer sem assinatura local e será processado pela Microsoft. O pacote MSIX continua instalado pela Store no contexto do usuário atual; `runFullTrust` permite executar o aplicativo desktop, mas não transforma a implantação em uma instalação para todos os usuários.

O script exige o .NET SDK e o Windows 10/11 SDK instalados pelo Visual Studio Installer. Os MSIs não são self-contained: a máquina de destino precisa ter o .NET Desktop Runtime 10 e o Windows App SDK Runtime 1.8 da arquitetura correspondente. Se `ORGANESSONIUM_PFX_PATH` estiver definido, o script usa o `SignTool` oficial para assinar os executáveis portáteis e os MSIs e, quando os pacotes da Store são gerados, também os MSIX e o MSIXBundle; a senha pode ser passada apenas no ambiente por `ORGANESSONIUM_PFX_PASSWORD`, sem ser gravada no repositório. `ORGANESSONIUM_TIMESTAMP_URL` é opcional. O MSI destinado a distribuição pública deve ser assinado com um certificado confiável.

Ao final, o script valida conteúdo, arquitetura, versão, identidade e encoding de cada artefato, descompacta administrativamente os três MSIs e recompila uma extração limpa do ZIP. Para solicitar o Windows App Certification Kit, execute `build-releases.bat -RunWack` em um terminal elevado. A ausência ou falha do WACK é reportada sem apagar os demais artefatos; a certificação final e a associação da identidade ainda dependem do Partner Center.
